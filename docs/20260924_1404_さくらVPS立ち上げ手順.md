# さくらVPS 立ち上げ手順

作成日: 2026-09-24

[公開までのタスク分割](20260923_1740_公開までのタスク分割.md) の **T7（VPS 構築・公開）** の手順書。
契約済みで停止しているさくらのVPS（2GB）を、「公開の直前」の状態まで立ち上げる。

何をやるか・なぜやるかは [プロジェクト方針とやりたいこと整理](20260912_1528_プロジェクト方針とやりたいこと整理.md) §3（ドメイン）・§5（VPS）が正。
構成は [ローカル docker compose 検証手順](20260922_1716_ローカルdocker-compose検証手順.md) と
[検証結果](20260922_2100_ローカルdocker-compose検証結果.md) で手元で確かめたものを、そのまま VPS に持っていく。

## 1. 前提と方針

### 前提

- **本番はまだ動いていない。** 移すデータは無く、**VPS の DB は空から作る**
  （マイグレーション＋必要なマスタ＋議案＋管理者1人）。
  方針ドキュメントや検証手順にある「本番データでの予行演習」「本番（Supabase Cloud）の設定確認」は、
  存在しない本番を前提にした記述なので、この手順では行わない（§7 で消す）
- seed の議案（`packages/seed/main/sapporo-bills/`）は、PR #44 で架空のサンプルから
  **札幌市議会の実データ**（令和8年第1回定例会〜第3回定例会、129件）に置き換えてある。
  会派・委員会・タグ（マスタ）と合わせて、どちらも VPS に入れる（手順8）。
  ただし `pnpm seed` は全件を消してから入れるので使わず、削除しない専用のコマンド
  （マスタは `pnpm seed:master`、議案は `pnpm seed:bills`）を流す
- VPS は **さくらのVPS 2GB**。契約済みで、今は停止している

### 方針

- **立ち上げと公開を分ける。** T1（名称「デジ民」の商標）の判断が付くまでは公開しない。
  それまでは web・admin の手前の nginx で Basic 認証をかけ、関係者しか入れない状態で立ち上げる（手順9）
- **VPS 上でビルドしない。** web・admin は GitHub Actions（最初の1回は手元）でビルドし、成果物を rsync で送る
- **VPS の上で試行錯誤しない。** 設定ファイルはリポジトリの `infra/` に置き、PR でレビューしてから持っていく
- **2個目のプロジェクトを載せやすくする。** Supabase（Postgres）は共通基盤、アプリはプロジェクトごとのディレクトリと
  systemd unit、nginx は vhost を足せば増える形にする

## 2. 全体像

```
                     ┌─────────────── さくらのVPS（Ubuntu 24.04）───────────────┐
ブラウザ ──443──→ nginx（ホスト、TLS 終端、vhost）                              │
                   ├ gikai.ezocivic.tech       → 127.0.0.1:3004  web   (systemd)  │
                   ├ gikai-admin.ezocivic.tech → 127.0.0.1:3003  admin (systemd)  │
                   └ db.ezocivic.tech          → 127.0.0.1:8000  ┐                │
                                                                  ▼                │
                              docker compose（infra/compose.yml）                  │
                              nginx :8000 ─┬ /rest/v1/    → rest (PostgREST)       │
                                           ├ /auth/v1/    → auth (GoTrue)          │
                                           └ /storage/v1/ → storage (storage-api)  │
                                                            ↓                      │
                                                           db (Postgres 17)        │
                                                           127.0.0.1:5433          │
                     └─────────────────────────────────────────────────────────────┘

手元（WSL）── ssh -L 5433:127.0.0.1:5433 ──→ マイグレーション・psql
GitHub Actions ── ビルド → rsync ──→ /srv/gikai/{web,admin}
```

- **nginx は2段**（ホストの nginx → compose の nginx）。compose はローカル検証と同じものを使い回せる。
  そのかわり、利用者の IP を compose 側に正しく引き継ぐ設定が要る（手順7・§6）
- 外から届くのは 22 / 80 / 443 だけ。compose のポートと web・admin は `127.0.0.1` でしか待ち受けない

### ディレクトリ

```
/srv/
├── supabase/            # 共通基盤。リポジトリの infra/ をそのまま置く（手順7-1 の rsync）
│   ├── compose.yml
│   ├── .env             # 秘密情報（600）。rsync の対象外
│   ├── nginx/ db/       # compose の nginx と DB 初期化 SQL
│   ├── host-nginx/      # ホストの nginx の vhost（手順9 で /etc/nginx/ へコピーする）
│   ├── systemd/         # web・admin の unit（手順10 で /etc/systemd/system/ へコピーする）
│   ├── sudoers/         # デプロイ用（手順10 で /etc/sudoers.d/ へコピーする）
│   ├── scripts/ cron/   # バックアップと会話ログ削除（手順11）
│   └── volumes/         # DB と画像ファイルの実体。rsync の対象外
├── gikai/               # プロジェクトごと
│   ├── web/             # standalone の成果物（rsync で置き換わる）
│   ├── admin/
│   ├── web.env          # web の実行時の環境変数（600）
│   └── admin.env
└── backups/             # pg_dump と画像の tar（手順11）
```

## 4. 手順

### 手順1: コントロールパネルでの作業（人）

1. **OS をインストールする**: コントロールパネルのサーバー詳細から OS の再インストール（表記は画面に従う）を選び、
   **Ubuntu 24.04 LTS（amd64）** を入れる
   - 「スタートアップスクリプト」は使わない（何が入ったか分からなくなるため）
   - 管理ユーザーのパスワードは長いものにする（SSH ではパスワードを使わないが、コンソールからのログインで使う）
   - **SSH 公開鍵を登録する**（手元の WSL の `~/.ssh/id_ed25519.pub`。無ければ `ssh-keygen -t ed25519` で作る）
2. **パケットフィルターを設定する**: 許可するのは **SSH（22）と Web（80 / 443）だけ**
   - **OS の再インストールで設定は引き継がれない。** 再インストール直後の既定は **22 番のみ許可**なので、
     そのたびに 80 / 443 を足し直す。忘れると手順9 の certbot が通らない
     （[さくらのお知らせ](https://vps.sakura.ad.jp/news/vps-pf-vu/)）
3. インストールが終わるとサーバーは起動する。**IPv4 アドレス**（と IPv6 アドレス）を控える
4. 契約内容を控えておく（方針 §5 の宿題）: 月額、ゾーン（石狩か東京か）、
   **プランを上げる時にデータが残るか**（さくらのサポート情報で確認する）

### 手順2: 初回ログインと SSH の締め付け

```bash
# 手元（WSL）から。ユーザー名はコントロールパネルに表示されるもの（Ubuntu は通常 ubuntu）
ssh ubuntu@<IPv4>
```

```bash
sudo apt update && sudo apt full-upgrade -y
sudo timedatectl set-timezone Asia/Tokyo
timedatectl            # "System clock synchronized: yes" と "NTP service: active" を確認
sudo hostnamectl set-hostname ezocivic-vps1
```

時刻の同期は必ず確かめる。web のキャッシュの無効化は時計のずれに弱い（検証結果 §4-8）。

SSH をパスワードで入れないようにする:

```bash
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
sudo sshd -t && sudo systemctl reload ssh
```

**今のセッションを閉じずに**、別のターミナルから `ssh ubuntu@<IPv4>` で入れることを確かめてから次に進む。

手元の `~/.ssh/config` に足しておくと以降が楽になる:

```
Host ezocivic-vps1
  HostName <IPv4>
  User ubuntu
```

### 手順3: ファイアウォールと自動更新

パケットフィルター（さくら側）に加えて、サーバーでも絞る。

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
```

> **docker のポートは ufw をすり抜ける。** docker は iptables を直接書き換えるので、compose で `0.0.0.0` に公開したポートは
> ufw で閉じていても外から届く。`infra/compose.yml` は `127.0.0.1` にだけ公開しているので問題ないが、
> ポートを足す時は必ず `127.0.0.1:` を付ける。

セキュリティ更新を自動で入れる:

```bash
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # Yes
```

再起動が要る更新（カーネル）は自動では再起動しない。月に一度くらい `cat /var/run/reboot-required` を見て、手で再起動する。

> **22 番には常に総当たりが来る。** 立ち上げ直後から、海外のIPが SSH にログインを試み続ける
> （2026-09-29 に実機で確認。中国のIPから同時に3本の確立済み接続）。
> **手順2 で公開鍵認証のみにしてあるので入られることは無い**が、ログは汚れる。
> 接続元を絞るか `fail2ban` を入れるかは §7「決めること」で判断する。
> 今どれだけ来ているかは次で見られる。
>
> ```bash
> # 22 番の確立済み接続（今の自分の接続も出る。自分のIPは `echo $SSH_CLIENT` の先頭で分かる）
> ss -tn state established '( sport = :22 )'
> # 失敗したログイン試行の数
> sudo journalctl -u ssh --since today | grep -c "Invalid user\|Failed"
> ```

### 手順4: スワップ

2GB のメモリに対し、実測は約 660MiB（検証結果 §4-7）。余裕はあるが、Postgres の伸びと Next.js の一時的な膨らみに備えて 2GB 足す。

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swap.conf
sudo sysctl --system
free -h
```

### 手順5: Docker と Node.js を入れる

**Docker Engine**（公式の apt リポジトリ。Ubuntu の `docker.io` パッケージは古いので使わない）:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker ubuntu     # 入り直すと sudo なしで docker が使える
```

docker のログが際限なく増えないようにする:

```bash
sudo tee /etc/docker/daemon.json <<'EOF'
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
EOF
sudo systemctl restart docker
```

**Node.js**（web・admin の `server.js` を動かすため。ビルドはしない）:

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
node -v
```

> **Node のバージョンは CI と揃える。** 今の CI（`code_check.yml` など）は Node 20 で、Node 20 は 2026-04 にサポートが終わっている。
> ビルド（GitHub Actions）と実行（VPS）を **Node 22 に揃える**変更を §6 のデプロイ PR に含める。

### 手順6: DNS（人）

`ezocivic.tech` のネームサーバーは今 Xserver にあるので、**Xserver の DNS レコード設定**で次を足す。

|---|---|---|---|

### 手順7: Supabase（compose）を立ち上げる

**1. ファイルを置く**（手元のリポジトリ直下から）

```bash
# -t が要る。ssh は既定で端末を割り当てないので、付けないと sudo がパスワードを聞けずに失敗する
# （sudo: a terminal is required to read the password）
ssh -t ezocivic-vps1 'sudo mkdir -p /srv/supabase && sudo chown ubuntu: /srv/supabase'
rsync -av --exclude volumes --exclude .env infra/ ezocivic-vps1:/srv/supabase/
```

**2. 秘密情報を作る**（手元で。作り方は検証手順 §3 手順0 と同じ。**ローカル検証で使った値は使い回さない**）

```bash
openssl rand -hex 32   # JWT_SECRET
openssl rand -hex 24   # POSTGRES_PASSWORD
# ANON_KEY / SERVICE_ROLE_KEY は検証手順 §3 手順0 の node のワンライナーで作る
```

作った4つはパスワードマネージャーに保存する。`JWT_SECRET` を失うと、全員のログインと ANON_KEY を作り直すことになる。

**3. `/srv/supabase/.env` を作る**（VPS で。`chmod 600`）

```bash
POSTGRES_PASSWORD=<生成した値>
JWT_SECRET=<生成した値>
ANON_KEY=<生成した値>
SERVICE_ROLE_KEY=<生成した値>

SUPABASE_PUBLIC_URL=https://db.ezocivic.tech
SITE_URL=https://gikai.ezocivic.tech
ADDITIONAL_REDIRECT_URLS=https://gikai-admin.ezocivic.tech/api/auth/callback

JWT_EXPIRY=3600
RATE_LIMIT_ANONYMOUS_USERS=30
GATEWAY_PORT=8000
DB_PORT=5433
```

**4. 起動**

```bash
cd /srv/supabase
docker compose up -d
docker compose ps                                  # db / auth / storage が healthy、rest / nginx が Up（healthcheck が無い）
curl -s 127.0.0.1:8000/auth/v1/health              # GoTrue
curl -s 127.0.0.1:8000/storage/v1/status           # storage-api
```

`restart: unless-stopped` なので、VPS を再起動しても docker と一緒に上がる。

compose の nginx は、ホストの `127.0.0.1:8000` に来た通信の `X-Real-IP` をそのまま利用者の IP として信じる
（`infra/nginx/supabase.conf` の `set_real_ip_from`）。そのため **8000 番は `127.0.0.1` 以外に公開しない**、
**ホストの nginx は `X-Real-IP` を必ず上書きする**（手順9）。compose のネットワークは `10.203.0.0/24` に固定しているので、
VPS の他のネットワークと重なって起動できない時は `compose.yml` と `supabase.conf` の両方を直す。
このサブネット固定より前に `docker compose up` したことがある環境では、既存の `infra_default` ネットワークが古いサブネットのまま残る
（ゲートウェイが `10.203.0.1` でなくなり、`X-Real-IP` が採用されず全員が同じ IP に見える）。一度 `docker compose down` してから `up -d` し直す。

### 手順8: マイグレーション・マスタ・管理者

DB は VPS の外に出さないので、**手元から SSH トンネル越しに**流す。VPS に supabase CLI やリポジトリは置かない。

```bash
# 手元。-f で背景に回るので、ターミナルを分けなくてよい。オプションには意味がある（下の注意を読む）。
# 8000 は手順8 の最後（管理者の作成）で使うので、まとめて張っておく
ssh -f -N ezocivic-vps1 \
  -L 127.0.0.1:5433:127.0.0.1:5433 \
  -L 127.0.0.1:8000:127.0.0.1:8000 \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3

# 確認と停止
#   pgrep -af "ssh .*-L"    動いているトンネルの一覧
#   pkill -f "ssh .*-L"     全部止める

# 手元（リポジトリ直下。develop の最新にしておく）
export PROD_DB_URL="postgresql://postgres:<POSTGRES_PASSWORD>@127.0.0.1:5433/postgres?sslmode=disable"

# 流す前に、トンネルが本当に通っているか確かめる
psql "$PROD_DB_URL" -c "select version()"      # PostgreSQL 17.x が返れば OK

npx supabase migration up --include-all --db-url "$PROD_DB_URL"
psql "$PROD_DB_URL" -c "select id, public from storage.buckets"   # bill-thumbnails | t
psql "$PROD_DB_URL" -c "select name from prompts"                 # プロンプト3件（マイグレーションが入れる）
```

> 手元のローカル Supabase（`npx supabase start`）も 5433 を使っていないか確かめる。ぶつかる場合はトンネルの手元側のポートを変える。

> **トンネルで詰まりやすい点**（2026-09-29 に実際に踏んだもの）
>
> - **`ssh` のオプションを省かない。** keepalive が無いと、WSL のスリープや NAT のタイムアウトで
>   TCP が**半死**になる。プロセスは生きていてローカルの 5433 も待ち受け続けるので、
>   一見正常なのに接続だけがタイムアウトする。`ServerAliveInterval=30` で90秒で検知して終了し、
>   `ExitOnForwardFailure=yes` でポートを掴めなかった時に黙って動き続けるのを防ぐ
> - **local 側に `127.0.0.1:` を付ける。** 省くと ssh が `::1` にも bind しようとし、
>   IPv6 ループバックが無い WSL では `bind [::1]:5433: Cannot assign requested address` が出る（無害だが紛らわしい）
> - **`-N` はプロンプトを返さない。** リモートでコマンドを実行せずトンネルだけを保つオプションなので、
>   使っている間ずっと前面に居座る。**固まったのではない。** `-f` を付ければ認証後に背景へ回る。
>   `-f` を付け忘れて止まって見える時は、`Ctrl+Z` → `bg` でそのまま背景に送れる
> - **`export` はターミナルごと。** トンネルを張ったターミナルで `export` しても、
>   別のターミナルには引き継がれない。`$PROD_DB_URL` が空のまま `--db-url ""` で実行すると、
>   `failed to connect to host=127.0.0.1` という紛らわしいエラーになる。`echo "${PROD_DB_URL%%:*}"` が
>   `postgresql` を返すか先に見る
>
> 生きているか迷ったら、上の `psql ... select version()` が一番早い。
> TCP が繋がるだけでは判断できない（ssh はリモートに届かなくてもローカルの接続は受け付ける）。

**マスタ**: 会派11件・委員会14件（決算特別委員会の第一部・第二部を含む）・タグ13件を、seed の `data.ts` の実データから入れる。
`pnpm seed` は全件を消してから入れるので**使わない**。代わりに `pnpm seed:master`（`packages/seed/master/run.ts`）を流す。
既存データを削除せず、キー（tags は `label`、factions / committees は `name`）で突き合わせて差分のカラムだけ書くので、何度流してもよい。
定例会（`council_sessions`）と議案は、この後の「**議案**」で `pnpm seed:bills` から入れる。

マスタは Postgres ではなく Kong（REST API）越しに入れるので、**8000 番のトンネルを使う**。
このページの最初で 5433 と一緒に張ってあるはず。張っていなければ、同じオプションで単独で張る。

```bash
# 手元。手順9 が終わっていれば SUPABASE_URL を https://db.ezocivic.tech にしてトンネル不要
# （最初に 5433 と一緒に張っていれば不要）
ssh -f -N ezocivic-vps1 -L 127.0.0.1:8000:127.0.0.1:8000 \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3
```

### 手順9: ホストの nginx と TLS

```bash
sudo apt install -y nginx certbot python3-certbot-nginx apache2-utils
```

**1. vhost を置く**: `infra/host-nginx/` の3つのファイル
（`gikai.ezocivic.tech.conf` / `gikai-admin.ezocivic.tech.conf` / `db.ezocivic.tech.conf`）を
`/etc/nginx/sites-available/` に置き、`sites-enabled/` にリンクする。

**apt で入る `default` サイトは外す。** 残したまま certbot を流すと、証明書と 443 番の設定が
`default`（中身は nginx の Welcome ページ）に書き込まれ、https で来た通信が vhost に届かない
（2026-09-29 に実際に踏んだ。gikai が 200 の Welcome ページ、db が 404 を返した）。
代わりに、どの vhost にも当たらない通信（IP 直打ちなど）を黙って切る受け皿を置く。

```bash
# VPS。3つの vhost は手順7 の rsync で /srv/supabase/host-nginx/ に届いている
sudo rm /etc/nginx/sites-enabled/default
sudo tee /etc/nginx/sites-available/00-default.conf > /dev/null <<'EOF'
server {
  listen 80 default_server;
  server_name _;
  return 444;
}
EOF
sudo ln -sfn /etc/nginx/sites-available/00-default.conf /etc/nginx/sites-enabled/00-default.conf

for f in gikai.ezocivic.tech.conf gikai-admin.ezocivic.tech.conf db.ezocivic.tech.conf; do
  sudo cp "/srv/supabase/host-nginx/$f" /etc/nginx/sites-available/
  sudo ln -sfn "/etc/nginx/sites-available/$f" "/etc/nginx/sites-enabled/$f"
done
ls /etc/nginx/sites-enabled/   # 00-default.conf と 3 つの vhost だけ（default が無いこと）
```

中身の要点:

- `gikai` → `127.0.0.1:3004`、`gikai-admin` → `127.0.0.1:3003`、`db` → `127.0.0.1:8000`
- 3つとも `proxy_set_header X-Real-IP $remote_addr;` と `X-Forwarded-For $remote_addr;`（利用者が送った値を**上書き**する）、
  `X-Forwarded-Proto $scheme;`
- web・admin は AI の応答をストリーミングで返すので `proxy_buffering off;`
- `db` は `client_max_body_size 50m;`（サムネイルのアップロード）
- **公開前は `gikai` と `gikai-admin` に Basic 認証をかける**（次の 2.）。`db` にはかけない

**2. 公開前の Basic 認証**

アプリにも Basic 認証（`BASIC_AUTH_USER` など）はあるが、**web のものは画面（HTML）にしか効かず、`/api/chat` などは素通しになる**
（`web/src/middleware.ts` の `_isHtmlRequest`）。公開前は nginx で**全パスに**かける。

```bash
sudo htpasswd -c /etc/nginx/htpasswd-gikai <ユーザー名>
```

```nginx
# gikai / gikai-admin の server ブロックに。公開する時（T1 の後）にこの2行を消す
auth_basic "EZO CIVIC (preview)";
auth_basic_user_file /etc/nginx/htpasswd-gikai;
```

admin から web の `/api/revalidate` を呼ぶ通信も nginx を通ると 401 になる。PR #51 で、admin から web へは
`http://127.0.0.1:3004` に直接送るようにする（`ADMIN` 側の環境変数で向け先を変える）。

`db` に Basic 認証をかけないのは、ブラウザの supabase-js が別オリジンの API に認証情報を付けないため。
`db` は RLS（ポリシー無し＝全拒否）で守られていて、anon キーでは何も読めない（検証結果 §3 #8）。

**3. 証明書**

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d gikai.ezocivic.tech -d gikai-admin.ezocivic.tech -d db.ezocivic.tech \
  -m <連絡用メールアドレス> --agree-tos --redirect
sudo certbot renew --dry-run      # 自動更新（systemd timer）が通るか
```

**certbot は必ず 1.（`default` を外して vhost を置く）の後に流す。** 先に流すと上のとおり `default` に書き込まれる。
やり直す時は `default` を外してから同じコマンドを流し、「1: Attempt to reinstall this existing certificate」を選ぶ
（証明書を取り直さないので、Let's Encrypt の発行回数の制限を使わない）。

流した後、**https → https の転送ループが無いか**確かめる。certbot が 80 番用の
`if ($host = ...) { return 301 https://...; }` を 443 番の server ブロックにも入れることがあり
（2026-09-29 に db と gikai で起きた。gikai-admin は正常だった）、そうなると https でも 301 が返り続ける。

```bash
# VPS。3つとも 1 なら正常（80 番のブロックにだけある）。2 のファイルは 443 番側の if ブロック（3行）を手で消す
grep -c "return 301" /etc/nginx/sites-available/*.ezocivic.tech.conf

# 手元
curl -s https://db.ezocivic.tech/auth/v1/health                                # GoTrue の JSON
curl -s -o /dev/null -w "%{http_code}\n" https://gikai.ezocivic.tech/          # 401（Basic 認証）
curl -s -o /dev/null -w "%{http_code}\n" https://gikai-admin.ezocivic.tech/    # 401
curl -s -o /dev/null -w "%{http_code}\n" http://gikai.ezocivic.tech/           # 301（https へ）
```

## 7. 決めること・直すこと

### 決めること

| 論点 | 案 |
|---|---|
| バックアップの持ち出し先 | (a) 手元の WSL から毎日 `rsync` で取りに行く（無料。手元の PC が点いている時しか取れない）、(b) さくらのオブジェクトストレージ（月額が掛かる、国内のまま）。**まずは (a)**、公開後に (b) を検討 |
| サーバーログの保存期間と閲覧者 | journald の保存期間を決める（例: 30日、`SystemMaxRetentionSec=30d`）。LLM のエラー時に市民の発言がログに出るため。閲覧できるのは VPS に入れる人（今はあなただけ）。決めたらプライバシーポリシー第8条に足す |
| Storage を残すか | 今は storage-api を載せる（検証済み）。nginx の静的配信に替えると約 116MiB 減る（方針 §9-1）。メモリが苦しくなったら検討 |
| 管理者パスワードの最低文字数 | 今は 6（`GOTRUE_PASSWORD_MIN_LENGTH`）。議員に開放する前に見直す（T10） |
| IPv6 | 公開前に AAAA と nginx の `listen [::]:443` を足すか。足さなくても IPv4 で繋がる |
| **SSH への総当たり対策** | 立ち上げ直後から海外のIPが 22 番に来ている（手順3）。公開鍵認証のみなので入られはしないが、ログが汚れる。案: (a) さくらのパケットフィルターで **22 番の接続元を自分のIPに限定**する（一番効くが、IPが変わると自分も入れなくなる。自宅回線が動的IPなら要注意）、(b) `fail2ban` を入れて失敗の多いIPを自動で遮断する（IPが変わっても困らない）、(c) 何もしない（実害が無いため）。**公開までに (a) か (b) を決める。** 決めたら journald の保存期間（上の行）と合わせて考える |
