# AIインタビュー広場 インタビュー対象の抽象化（D2）

作成日: 2026-11-12

- 目的: 既存のインタビューと論点分析は議案（`bill_id`）を前提にしている。議題（`interview_topics`）でも同じ仕組みを使うために、
  「議案か議題か」をどこで吸収するかを決める
- 位置づけ: [実装タスク分割](20261112_2019_AIインタビュー広場_実装タスク分割.md) の **D2** の成果物。
  P1・P2b・P3b・P4・P8 はこのドキュメントを仕様として読む
- 前提: [機能設計 §3・§7](20261112_2009_AIインタビュー広場_機能設計.md)、[法案インタビュー機能DB設計](20251217_1831_法案インタビュー機能DB設計.md)
- このドキュメントはコードを変えない。決めたことは P1 以降で実装する

---

## 1. 結論

| # | 論点 | 決定 |
|---|---|---|
| 1 | DB の持ち方 | 既存テーブルを広げる。`interview_configs` と `topic_analysis_versions` の `bill_id` を任意にし、`interview_topic_id` を足して、**どちらか一方だけ**を持つ CHECK 制約を付ける |
| 2 | 列名 | `topic_id` ではなく **`interview_topic_id`**。論点分析で「topic」はすでに論点（`topic_analysis_topics`）の意味で使われているため |
| 3 | 議題のインタビュー設定の数 | **議題ごとに1つ**（部分ユニークインデックス）。議案のように複数の設定を作って切り替えることはしない |
| 4 | 受付可否の正 | **`interview_topics.status`**。議題の設定では `interview_configs.status` を使わない（既定値 `closed` のまま置く） |
| 5 | 作成者の外部キー | `on delete set null`（機能設計 §7-1 の `restrict` から変更）。表示にはオープン時点の写しを使う |
| 6 | アプリ側の型 | 参照 `InterviewSubjectRef`（`{ kind, id }`）と、中身 `InterviewSubject`（種類・ID・タイトル・名前・要約・本文）。`packages/shared` に置き、web と admin の両方で使う |
| 7 | 型エラーになる既存コード | 4か所だけ。P1 で、議案の振る舞いを変えずに直す（§5-1） |
| 8 | 型は通るが議題で壊れる箇所 | 手書きの型で `bill_id: string` と決め打ちしている読み出しがある。議題のセッションが通るようになる P4・P7・P10 で直す（§5-2） |

## 3. DB の持ち方

### 3-1. 比較

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A（採用）** | `interview_configs` と `topic_analysis_versions` に `interview_topic_id` を足し、`bill_id` と排他にする | セッション・メッセージ・個別レポート・論点・分類は設定やバージョンにぶら下がっているので、**そのまま使える**。既存の議案のクエリ（`.eq("bill_id", ...)`）は議題の行に当たらないので、既存の振る舞いが変わらない | 「どちらか一方」を CHECK で守る必要がある。読み出し側に「どちらの対象か」の分岐が入る |
| B | 議題用に `topic_interview_configs` などの別テーブルを作る | 議案側に一切触らない | `interview_sessions.interview_config_id` が1つの表しか指せないので、セッション以下も二重に持つことになる。インタビューと分析のパイプラインを流用できない |
| C | `interview_subjects` のような親テーブルを作り、議案と議題がそれぞれ1行を持つ | 対象の種類を足すときに広げやすい | 既存の議案の設定・分析をすべて移行する必要があり、`bill_id` で引いている既存コード（§2）を一度に書き換えることになる。広場の初版には過大 |

対象の種類が議案と議題の2つから増える見込みは今のところ無いので、移行コストの小さい A を採る。

### 3-2. 決定（P1 で実装）

**`interview_configs`**

```sql
alter table public.interview_configs
  alter column bill_id drop not null,
  add column interview_topic_id uuid
    references public.interview_topics(id) on delete cascade,
  add constraint interview_configs_subject_exactly_one
    check (num_nonnulls(bill_id, interview_topic_id) = 1);

create unique index idx_interview_configs_interview_topic_id
  on public.interview_configs (interview_topic_id)
  where interview_topic_id is not null;
```

- **議題の設定は1つ**。機能設計 §3 の「インタビュー設定（テーマと質問）ができている必要がある」は1つを前提にしており、
  「回答が始まったか」（その議題の設定にセッションが1件でもあるか）の判定も単純になる。既存の「設定の複製」は議題には出さない
- **受付可否は `interview_topics.status` だけで判定する**。議題の設定の `status` は使わず、既定値の `closed` のまま置く。
  議題の状態と設定の状態を両方持つと、片方だけ更新されたときにどちらが正しいか分からなくなるため。
  P4 の「対象から設定を引く」関数は、議案なら従来どおり `status = 'public'` の設定を、議題なら議題に紐づく唯一の設定を返す
- 削除は議案と同じく cascade。議題の削除は「回答が始まる前だけ」（機能設計 §2 の14）をアプリ層で守る

**`topic_analysis_versions`**

```sql
alter table public.topic_analysis_versions
  alter column bill_id drop not null,
  add column interview_topic_id uuid
    references public.interview_topics(id) on delete cascade,
  add constraint topic_analysis_versions_subject_exactly_one
    check (num_nonnulls(bill_id, interview_topic_id) = 1),
  add constraint topic_analysis_versions_interview_topic_id_version_key
    unique (interview_topic_id, version);
```

- 既存の `UNIQUE (bill_id, version)` は `bill_id` が null の行には効かない（null どうしは別物として扱われる）ので、議題の側にも同じユニーク制約を張る

**`interview_topics.author_user_id`**

- 機能設計 §7-1 は `on delete restrict` だったが、**`on delete set null`** にする。
  既存のアカウント削除（`admin/src/features/admins/server/actions/delete-account.ts`）は `admin_profiles` の行を消すので、
  restrict だと議題を1つでも作った人はアカウントを削除できなくなる。K7 は「議題は残す」なので、外部キーを外して写しで表示する
- そのため、公開した議題（`open` / `closed`）は作成者の写し（表示名・ロール）を必ず持つ（CHECK 制約）
- 作成者が削除された**下書き**は、作成者が null のまま残る。誰も編集できないので、P2 で「アカウント削除時に下書きを消すか」を決める（§6-1）

議題 → 回答 → 個別レポートは、次のように辿る。

```sql
select r.*
from interview_topics t
join interview_configs c on c.interview_topic_id = t.id
join interview_sessions s on s.interview_config_id = c.id
join interview_report r on r.interview_session_id = s.id
where t.id = $1;
```

## 4. アプリ側の型

### 4-1. 型

`packages/shared/src/interview-subject/` に置く（web と admin の両方が `@dejimin-gikai/shared` に依存している）。
`package.json` の `exports` に `./interview-subject` を足す。

```ts
/** インタビューの対象の種類 */
export type InterviewSubjectKind = "bill" | "topic";

/** 対象の参照。API の入力・URL・キャッシュキー・repository の引数に使う */
export type InterviewSubjectRef = {
  kind: InterviewSubjectKind;
  id: string;
};

/** プロンプトと画面に渡す対象の中身 */
export type InterviewSubject = {
  ref: InterviewSubjectRef;
  /** 見出し。議案: bill_contents(normal).title ?? bills.name ／ 議題: interview_topics.title */
  title: string;
  /** 正式名。議案: bills.name ／ 議題: title と同じ */
  name: string;
  /** 要約。議案: bill_contents(normal).summary ／ 議題: 空文字（扱いは D3 で決める） */
  summary: string;
  /** 本文（Markdown）。議案: bill_contents(normal).content ／ 議題: interview_topics.body_md */
  bodyMd: string;
};
```

- 参照は `{ kind, id }` の1つの形にする。`{ kind: "bill"; billId } | { kind: "topic"; topicId }` のような判別共用体にすると、
  JSON（API の body）と URL での受け渡し、キャッシュキーの組み立てが種類ごとに分かれてしまうため
- 中身は、既存のプロンプトが議案から取り出している4つ（名前・タイトル・要約・本文）に合わせる。
  議案の値の取り方は、`loop-mode.ts` / `build-summary-system-prompt.ts`（web）と `fetchBillWithContents`（admin）の現在の取り方と同じにする
- 議題の作成者（写し）や状態は、この型に入れない。画面では議題の行をそのまま使い、プロンプトに作成者を渡すかは D3 で決める

### 4-2. 純粋関数（`packages/shared/src/interview-subject/` に置き、テストを付ける）

| 関数 | 内容 |
|---|---|
| `subjectRefFromConfig(config: { bill_id: string \| null; interview_topic_id: string \| null }): InterviewSubjectRef` | 設定の行から参照を作る。両方 null・両方あり（DB の制約で起きない）は例外にする |
| `subjectColumn(ref): "bill_id" \| "interview_topic_id"` | repository で `.eq(subjectColumn(ref), ref.id)` と書くための列名 |
| `subjectFromTopic(topic): InterviewSubject` | 議題の行から中身を作る |
| `parseSubjectRef(value: unknown): InterviewSubjectRef \| null` | API の body の検証（zod でもよい） |

議案から中身を作る関数は、議案の型が web（`BillWithContent`）と admin（`bills` の行と `bill_contents` の配列）で違うので、
それぞれのアプリの `shared/utils/` に `subjectFromBill` として置く。

### 4-3. 置き換えの方針

- server 側の関数は `billId: string` の代わりに `subject: InterviewSubjectRef` を受け取る
- 「対象の中身を引く」関数を1つにまとめる（web: `getInterviewSubject(ref)`、admin: `fetchInterviewSubject(ref)`）。
  中で議案なら議案を、議題なら議題を引き、`InterviewSubject` にして返す
- プロンプトを組み立てる純粋関数は `bill: BillWithContent | null` の代わりに `subject: InterviewSubject | null` を受け取る。
  **議案のときの出力文字列は1文字も変えない**（P4 の完了条件。既存のテストの期待値を変えずに通す）
- 議題用の文面（「法案名」ではなく「議題」、賛否を聞かない、など）は D3 で決め、P7・P8 で `subject.ref.kind` を見て切り替える

## 5. `bill_id` を任意にしたときの既存コード

### 5-1. 型エラーになる箇所（P1 で直す）

P1 のマイグレーションを当てて型を再生成すると、`pnpm typecheck` で次の4か所が落ちる。いずれも**議案の振る舞いを変えずに**直す。

## 6. 各タスクへの引き継ぎ

### 6-1. P1（DB スキーマ）

- §3-2 のとおり `interview_configs` と `topic_analysis_versions` を広げる。列名は `interview_topic_id`
- `interview_topics` は機能設計 §7-1 に、作成者の写し（`author_display_name` / `author_role` / `author_faction_name`）と取り下げ（`withdrawn_at` / `withdrawn_reason`）を足す。
  作成者の外部キーは `on delete set null`
- 1行の中の整合は CHECK 制約で、更新前後を比べる規則（状態は 下書き → オープン → クローズ の順にしか進めない、
  オープン後はオープン日時・期限・作成者の写しを変えない、クローズ後はクローズ日時と理由を変えない）は `BEFORE UPDATE` トリガーで守る
- §5-1 の4か所を直す
- 監査ログのトリガーを `interview_topics` に張る
- seed: `TABLES_TO_CLEAR` に `interview_topics` を足す。議題の作成者になる議員・候補者のアカウントを seed で作る（`seed.sql` の運営者は K3 により議題を出せない）
- P2 への申し送り
  - 作成者のアカウントを削除したとき、その人の**下書き**は作成者が null のまま残る。消すか残すかを P2 で決める
  - 監査ログの画面（`admin/src/features/audit-logs/` の `AUDIT_TARGET_TABLES` と表示名）に `interview_topics` を足す。
    P1 で足すと、機能フラグがオフの間も絞り込みの選択肢に「議題」が出てしまうので、admin から議題を書き込むようになる P2 で足す。
    それまでに記録される行（seed など）は、テーブル名のまま表示される

### 6-2. P2b（admin: インタビュー設定）

- 議題の設定は1つ。作成は「議題に設定が無ければ作る、あれば更新する」にし、既存の一覧・複製・公開切り替え（`closeOtherPublicConfigs`）は議題では使わない
- 設定の `status` は触らない（既定値 `closed` のまま）。受付可否は議題の状態で決まる
- 既存のフォームと AI 生成のチャットは、`billId` の代わりに `InterviewSubjectRef` を受け取る形にして流用する。
  `handle-config-generation.ts` の議案の取得を `fetchInterviewSubject(ref)` に置き換え、プロンプトには `InterviewSubject` を渡す（文面は D3）
- `/api/interview-config/generate` の body は `billId` の代わりに `subject: { kind, id }` を受け取る。議案の画面からの呼び出しも合わせて変える
- 認可は「`kind` が `bill` なら運営者だけ、`topic` なら自分の議題の作成者だけ」を、Server Action と API ルートの先頭で確かめる
- 「回答が始まった」は「その議題の設定に `interview_sessions` が1件でもある」（やり直しでアーカイブされたセッションも数える）

### 6-3. P3b（admin: 回答の閲覧）

- `findInterviewConfigIdByBillId(billId)` を、対象の参照から設定を引く関数に置き換える。議題では議題に紐づく唯一の設定を引く（`status` を見ない）
- `get-interview-sessions.ts` 以下の一覧・詳細はそのまま流用できる。違うのは、設定を引く起点と、リンク先のパス（`/plaza-topics/[id]/responses/...`）だけ
- `update-report-visibility.ts` の再検証パスは、対象の種類で分ける

### 6-4. P4（web: リファクタリング）

- §4 の型と純粋関数を `packages/shared/src/interview-subject/` に作る
- §2-2 の「担当 P4」の箇所を、`InterviewSubjectRef` / `InterviewSubject` を受け取る形に変える
- API（`/api/interview/chat`）の body は `billId` の代わりに `subject: { kind, id }` を受け取る。クライアントも合わせて変える
- 「対象から設定を引く」関数は、議案なら従来の `getInterviewConfigAdmin(billId)`（public を優先し、無ければ最新）と同じ結果を返す。議題の分岐は口だけ用意し、P7 で中身を入れてもよい
- §5-2 の `get-interview-session-by-id.ts` を `subjectRefFromConfig` に置き換える
- プロンプトの出力は議案で1文字も変えない（既存テストの期待値を変えない）

### 6-5. P8（admin: 論点分析）

- `createVersion` / `findVersionsByBillId` / `fetchCompletedInterviewReports` を、対象の参照を受け取る形に変える（`.eq(subjectColumn(ref), ref.id)`）。
  バージョン番号は対象ごとに採番する（DB のユニーク制約も対象ごと）
- 議題のときは、分析の対象を「クローズ時点で完了しているインタビュー」に絞る（`completed_at <= closed_at`、機能設計 §6-1）
- `fetchBillWithContents` を `fetchInterviewSubject(ref)` に置き換え、`InterviewSubject` の `title` / `summary` をプロンプトへ渡す
- `PhaseData.bill_title` / `bill_summary` は DB の `phase_data` に保存されているので、名前を変えるなら**古い名前も読めるようにする**（実行中のバージョンを壊さないため）
- `validate-references.ts` の引用リンクは admin のパス（`/bills/{id}/reports/{sessionId}`）で作られている。
  議題では admin の `/plaza-topics/{id}/responses/{sessionId}` にするか、web で表示する P10 に合わせてリンクを外すかを、P8 と P10 で揃える
- API ルート（`/api/topic-analysis/run`・`phases/*`）の body も `billId` から `subject` に変える

## 7. 決めなかったこと

| 論点 | 理由 | 決めるタスク |
|---|---|---|
| 議題の要約（`InterviewSubject.summary`）を何にするか（空・本文の冒頭・作成者が書く） | プロンプトの文面と一緒に決めるべきなので | D3 |
| プロンプトに作成者（名前・会派）を渡すか | 回答への影響（作成者への忖度）を考える必要があるので | D3 |
| 作成者のアカウント削除時に下書きを消すか | アカウント削除の画面の挙動に関わるので | P2 |
| 取り下げた議題を状態としてどう扱うか（クローズするか、状態は残して非表示にするだけか） | 取り下げの運用と一緒に決めるべきなので。P1 では日時と理由の列だけを用意する。なお、オープンのまま取り下げると、「オープンは1人1つ」の部分ユニークインデックスがその作成者の枠を使い続ける（インデックスは `withdrawn_at` を見ていない）。オープン中の取り下げをクローズとして扱うか、インデックスの条件を変えるかを決める | P11 |
