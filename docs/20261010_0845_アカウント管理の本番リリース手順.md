## 2. メールの送信サービスを用意する（人・初回だけ）

招待とパスワード再設定のメールを `noreply@ezocivic.tech` から送るための SMTP サーバーを用意する。
送るのは月に数十通程度。**本番アクセスの審査に最大1日かかる**ので、リリースの数日前に始める。

### 2-1. どれにするか

| | Amazon SES（東京リージョン）**推奨** | Resend |
|---|---|---|
| 送る場所 | 日本（`ap-northeast-1`） | 米国が既定。東京から送る設定は有料プランだけの可能性がある（契約前に確かめる） |
| 宛先・送信ログの置き場所 | 日本（東京リージョン） | **米国**（送る地域を変えても、アカウントのデータは米国に置かれる） |
| 料金 | 従量課金。月数十通なら数円〜数十円 | 無料枠（1日100通） |
| 手間 | AWS アカウント・本番アクセスの申請（審査あり）・SMTP 認証情報の作成が要る | 一番簡単（ドメインを足して DNS を入れるだけ） |

**推奨は Amazon SES の東京リージョン。** プライバシーポリシー第5条に「サーバーおよびデータベースは日本国内のデータセンターで運用しています」
と書くので、議員・出馬者のメールアドレスと送信の記録も国内に置いておくほうが説明が揃う。
AWS アカウントを作るのが重すぎる場合は Resend でもよい（§2-4）。

料金と無料枠は変わることがある（SES は 2026年7月に料金プランが変わった）。契約前にそれぞれの公式の料金ページで確かめる。

### 2-2. Amazon SES の作り方

**画面の右上のリージョンを「アジアパシフィック（東京）ap-northeast-1」にしてから始める。** SES はリージョンごとに別物で、
認証情報もリージョンごとに違う。

**a. AWS アカウント** — 無ければ作る。ルートユーザーに MFA を付け、請求アラート（例: 月 5 USD）を設定しておく。

**b. ドメインを登録する**（SES → 設定 → ID → ID の作成）

| 項目 | 値 |
|---|---|
| ID タイプ | ドメイン |
| ドメイン | `ezocivic.tech` |
| カスタム MAIL FROM ドメインを使用 | オン。`bounce`（= `bounce.ezocivic.tech`）。MX が見つからない時の動作は「デフォルトの MAIL FROM ドメインを使用」 |
| 検証（DKIM） | Easy DKIM、RSA_2048_BIT。「Route 53 に DNS レコードを発行」はオフ（DNS は Xserverドメイン） |

作ると、DNS に入れるレコード（DKIM の CNAME 3つと、MAIL FROM の MX・TXT）が画面に出る。

**c. DNS に入れる**（Xserverドメイン → ドメイン → DNSレコード設定）

| 種別 | ホスト名 | 値 | 用途 |
|---|---|---|---|
| CNAME | `<トークン1>._domainkey` | `<トークン1>.dkim.amazonses.com` | DKIM（SES の画面の3行をそのまま） |
| CNAME | `<トークン2>._domainkey` | `<トークン2>.dkim.amazonses.com` | 〃 |
| CNAME | `<トークン3>._domainkey` | `<トークン3>.dkim.amazonses.com` | 〃 |
| MX | `bounce` | `feedback-smtp.ap-northeast-1.amazonses.com`（優先度 10） | 不達メールの受け取り（MAIL FROM） |
| TXT | `bounce` | `v=spf1 include:amazonses.com ~all` | SPF（MAIL FROM のドメインで判定される） |
| TXT | `_dmarc` | `v=DMARC1; p=none` | DMARC。まずは観測だけ（§6） |

- ホスト名の欄は、画面が後ろに `.ezocivic.tech` を付けるなら、その前の部分だけを入れる。二重に付くと `xxx._domainkey.ezocivic.tech.ezocivic.tech` になって通らない
- **`ezocivic.tech` そのもの（ホスト名が空）の SPF は足さなくてよい。** SPF はカスタム MAIL FROM（`bounce.ezocivic.tech`）で判定される。
  既に `v=spf1` の TXT がある場合も、そのままにする（SPF の TXT は1つのホスト名に1つまで）
- `_dmarc` に既にレコードがあれば足さずに中身を見る

入ったかどうかは手元で確かめる（反映には数分〜数時間かかる）:

```bash
dig +short CNAME <トークン1>._domainkey.ezocivic.tech   # <トークン1>.dkim.amazonses.com.
dig +short MX bounce.ezocivic.tech                      # 10 feedback-smtp.ap-northeast-1.amazonses.com.
dig +short TXT bounce.ezocivic.tech                     # "v=spf1 include:amazonses.com ~all"
dig +short TXT _dmarc.ezocivic.tech                     # "v=DMARC1; p=none"
```

SES の ID の画面で、「ID のステータス」と「DKIM の設定」が「検証済み」、「カスタム MAIL FROM ドメイン」が「成功」になれば済み。

**d. 本番アクセスを申請する**（SES → アカウントダッシュボード → 本番アクセスのリクエスト）

作ったばかりの SES は「サンドボックス」で、**SES に登録したアドレスにしか送れない**（議員のアドレスに送ると拒否される）。
申請は次のように書けばよい（日本語で出せる）。

| 項目 | 値 |
|---|---|
| メールタイプ | トランザクション |
| ウェブサイトの URL | `https://gikai.ezocivic.tech` |
| ユースケースの説明 | 下の例 |

```
札幌市議会の議案を市民向けに解説するサイト「デジタル民主主義共創議会」（https://gikai.ezocivic.tech）の運営者です。
管理画面（運営者・市議会議員・出馬予定者の数十名のみが利用）の、アカウント招待メールとパスワード再設定メールだけを送ります。
宣伝やメールマガジンは送りません。送信数は月に数十通程度です。
宛先は、運営者が本人確認（議会事務局経由、または公式に公開されている連絡先）をしたうえで管理画面から登録したアドレスだけで、
一般の利用者はアドレスを登録できません。
差出人は noreply@ezocivic.tech で、ドメインは DKIM・SPF（カスタム MAIL FROM）・DMARC で認証しています。
不達と苦情は SES のアカウントレベルのサプレッションリストで送信を止めます。
```

返事は通常24時間以内に届く。承認されるまでは §3 の招待の確認（§3-6 #3）ができないが、ほかの手順は進められる。

**e. SMTP の認証情報を作る**（SES → SMTP 設定 → SMTP 認証情報の作成）

IAM ユーザーが作られ、SMTP のユーザー名とパスワードが**1度だけ**表示される。CSV をダウンロードして、
パスワードマネージャーに保存する（構築手順 §2「秘密情報の一覧」）。

| 値 | 中身 |
|---|---|
| SMTP のホスト | `email-smtp.ap-northeast-1.amazonaws.com` |
| ポート | `587`（STARTTLS） |
| ユーザー名・パスワード | 作成時に表示された値（IAM のアクセスキーとは別物。東京リージョン専用） |

**f.（任意）差出人を `noreply@` に絞る** — 作られた IAM ユーザーのポリシーは「どの差出人でも送れる」なので、
漏れた時の被害を小さくするなら、インラインポリシーを次のものに置き換える。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ses:SendRawEmail",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "ses:FromAddress": "noreply@ezocivic.tech" }
      }
    }
  ]
}
```

### 2-3. VPS から SES に届くか

```bash
ssh ezocivic-vps1 'nc -zv -w 5 email-smtp.ap-northeast-1.amazonaws.com 587'   # succeeded と出れば届く
```

### 2-4. Resend にする場合

1. Resend でドメイン `ezocivic.tech` を足す（地域を選べるなら Tokyo）
2. 画面に出る DKIM（`resend._domainkey` の TXT）と SPF（`send` の MX・TXT）を Xserverドメインに入れ、`_dmarc` は §2-2 c と同じ
3. API キーを「Sending access」・ドメイン `ezocivic.tech` に絞って作る
4. SMTP の値は ホスト `smtp.resend.com`・ポート `587`・ユーザー名 `resend`・パスワードは API キー

### 3-1. `develop` → `main`

`/deploy` で `develop` → `main` の PR を作ってマージする。**Deploy VPS はまだ流さない**（3-5 で流す）。
`/deploy` はマイグレーションと `infra/` の差分を一覧にするので、§0 の7本と `infra/` の変更が入っていることを確かめる。

`main` が 9/29 のままなので、`infra/` の差分には `host-nginx/`・`systemd/`・`cron/`・`scripts/` も出る。
これらは VPS の構築（手順7〜11）の時に `develop` から置いてあり、10/1 より後の変更はコメントと

3-4 の `compose.yml`・`nginx/supabase.conf`・`email-templates/`（`/srv/supabase/` に送って `docker compose up -d`）だけ。

置き場所を変えて取る。この置き場所も、14日たつと毎朝の cron が古いものとして消す。

```bash

ssh -t ezocivic-vps1 'BACKUP_ROOT=/srv/backups/pre-release /srv/supabase/scripts/backup.sh && ls -la /srv/backups/pre-release/$(date +%Y%m%d)'
```

```bash
# 手元（リポジトリ直下）。3-1 の後なら main。3-1 の前に急いで当てる時は、ここを git switch --detach "$deployed" にする（§1-3。$deployed は 1-1 と同じシェルで作る）
```

### 3-3. `/srv/supabase/.env` に足す

パスワードをシェルの履歴に残さないよう、エディタで開いて足す。

```bash
ssh -t ezocivic-vps1 'nano /srv/supabase/.env'
```

```bash
# 招待・再設定メールのリンク先。VPS を作った時（9/30）の手順7 では …/api/auth/callback だったので、

ADDITIONAL_REDIRECT_URLS=https://gikai-admin.ezocivic.tech/update-password
```

### 3-4. `infra/` を送って compose を作り直す

compose の nginx（メールのテンプレートを中から配る 8088 番）と、`infra/email-templates/` が増えている。


## 4. うまくいかない時

| 症状 | 原因と直し方 |
|---|---|
| 招待は「送りました」と出るのに届かない | `docker compose logs auth --since 10m \| grep -i -E "smtp\|mail"` を見る。`SMTP_HOST` が空（3-3 の後に `docker compose up -d` したか）、迷惑メールフォルダ、下の SES のエラー |
| ログに `554 Message rejected: Email address is not verified` | SES がまだサンドボックス。§2-2 d の承認を待つ（それまでは SES に登録したアドレスにしか送れない） |
| ログに `535 Authentication Credentials Invalid` | SMTP のパスワードの取り違え（IAM のアクセスキーを入れていないか）、別のリージョンで作った認証情報 |
| 英語のメール（「You have been invited」）が届き、リンクを開くと「リンクを確認できません」 | GoTrue がテンプレートを取れていない。3-4 の `grep -c token_hash` が 1 か、`docker compose logs auth \| grep templatemailer`（構築手順 手順13 の「詰まりやすい点」） |
| メールのリンクが web（`gikai.ezocivic.tech`）に飛ぶ | `ADDITIONAL_REDIRECT_URLS` に `https://gikai-admin.ezocivic.tech/update-password` が無い。足して `docker compose up -d` |
| 招待すると「リンク先（NEXT_PUBLIC_APP_URL）が設定されていない」 | `NEXT_PUBLIC_*` はビルド時にサーバーのコードにも埋め込まれるので、`admin.env` を直しても効かない。GitHub の Variables の `NEXT_PUBLIC_APP_URL`（`https://` から始まる `https://gikai-admin.ezocivic.tech`）を直し、Deploy VPS を流し直す（構築手順 手順10-3） |
| compose を更新したら web のチャットが始まらない（匿名ログインが失敗） | フックの関数が無い。3-2 のマイグレーションを当てる（フックを外すより早い） |
| admin の「アカウント」画面がエラー | `get_admin_accounts()` が無い。3-2 のマイグレーションを当てる |
| 迷惑メールに入る | §2-2 c の DNS。`dig` の結果と、Gmail のソースの SPF・DKIM・DMARC を見る |
| Deploy VPS が「デプロイできるのは main ブランチだけです」で止まる | `--ref main` を付けたか。画面からなら Use workflow from を `main` にする |
| 招待が「1時間あたりの送信数の上限」で止まる | `RATE_LIMIT_EMAIL_SENT`（既定 30）。一時的に上げて `docker compose up -d`、終わったら戻す（構築手順 手順13-8） |

## 6. 決めること（人）

| 論点 | 案 |
|---|---|
| **メールの送信サービス** | §2-1。推奨は Amazon SES の東京リージョン |
| DMARC を厳しくする時期 | まずは `p=none`。1〜2か月 SPF・DKIM が通り続けたら `p=quarantine` にする。集計レポート（`rua=mailto:...`）を受けるには受信できるアドレスが要る（`noreply@` は受信しない） |
| `main` への push で自動デプロイにするか | 今は手動実行のみ（マイグレーションや `infra/` を先に当てるため）。公開後、マイグレーションの無いリリースが続くなら `deploy_vps.yml` の `push:` を有効にしてもよい |
| デプロイを本当に `main` だけに絞るか | ワークフローの「`main` 以外は止める」は指定違いを防ぐだけで、権限の制限ではない（ワークフローのファイルはどのブランチでも書き換えられ、デプロイ鍵は repository の Secrets にある）。絞るなら、Environment（例: `vps-production`）を作って Deployment branches を `main` だけにし、`VPS_SSH_PRIVATE_KEY`・`VPS_SSH_KNOWN_HOSTS` をそこへ移して、`deploy_vps.yml` に `environment: vps-production` を足す（Settings の作業は人、ワークフローは PR）。今は push できるのが運営者だけなので急がない |
| Deploy Web（`deploy_web.yml`）を消すか | Vercel の Deploy Hook を呼ぶワークフロー（福岡市版から引き継いだもの）。この repo の Secrets にフックの URL（`WEB_VERCEL_DEPLOY_HOOK_URL`）が無く、`develop` への push のたびに `curl -X POST ""` で失敗している。構築手順 §6 でも公開時に消すことになっている |
| Vercel のプロジェクトを止めるか | Actions とは別に、Vercel の GitHub 連携（`project-5ki8w`）がまだこの repo に繋がっていて、PR ごとにプレビューをビルドしている（PR #78 の vercel[bot] のコメント）。どのブランチを Vercel の本番にするかは Vercel の Settings → Git の Production Branch で決まり、repo からは見えない。本番は VPS なので、構築手順 §6 のとおり止めるか、残すなら Production Branch を確かめる（人） |
