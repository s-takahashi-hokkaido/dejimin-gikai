## 1. 前提と方針

### 前提

- **本番はまだ動いていない。** 移すデータは無く、**VPS の DB は空から作る**（マイグレーション＋マスタ＋議案＋管理者1人）
- seed の議案（`packages/seed/main/sapporo-bills/`）は PR #44 で**札幌市議会の実データ**（令和8年第1回定例会〜第3回定例会、129件）に置き換えてある。
  マスタ（会派・委員会・タグ）と合わせて VPS に入れる。ただし `pnpm seed` は全件を消してから入れるので**使わない**。
  削除しない専用のコマンド（`pnpm seed:master`・`pnpm seed:bills`）を使う
- VPS は **さくらのVPS 2GB**（Ubuntu 24.04）

### 方針

- **立ち上げと公開を分ける。** T1 の判断が付くまでは、web・admin の手前の nginx で Basic 認証をかける
- **VPS 上でビルドしない。** web・admin は GitHub Actions でビルドし、成果物を rsync で送る
- **VPS にリポジトリを置かない。** 設定ファイルはリポジトリの `infra/` に置き、PR でレビューしてから rsync / scp で持っていく。
  DB の操作は手元から SSH トンネル越しに行う
- **2個目のプロジェクトを載せやすくする。** Supabase（Postgres）は共通基盤、アプリはプロジェクトごとのディレクトリと
  systemd unit、nginx は vhost を足せば増える形にする

何をやるか・なぜやるかの元は [プロジェクト方針](20260912_1528_プロジェクト方針とやりたいこと整理.md) §3（ドメイン）・§5（VPS）。
構成は [ローカル docker compose 検証手順](20260922_1716_ローカルdocker-compose検証手順.md) と
[検証結果](20260922_2100_ローカルdocker-compose検証結果.md) で手元で確かめたものを、そのまま VPS に持っていっている。

## 2. 全体像

```
                     ┌─────────────── さくらのVPS（Ubuntu 24.04）───────────────┐
ブラウザ ──443──→ nginx（ホスト、TLS 終端、vhost）                              │
                   ├ gikai.ezocivic.tech       → 127.0.0.1:3004  web   (systemd)  │
                   ├ gikai-admin.ezocivic.tech → 127.0.0.1:3003  admin (systemd)  │
                   └ db.ezocivic.tech          → 127.0.0.1:8000  ┐                │
                                                                  ▼                │
                              docker compose（infra/compose.yml）                  │
                              nginx :8000 ─┬ /rest/v1/    → rest (PostgREST)       │
                                           ├ /auth/v1/    → auth (GoTrue)          │
                                           └ /storage/v1/ → storage (storage-api)  │
                                                            ↓                      │
                                                           db (Postgres 17)        │
                                                           127.0.0.1:5433          │
                     └─────────────────────────────────────────────────────────────┘

手元（WSL）── SSH トンネル 5433 / 8000 ──→ マイグレーション・psql・seed
GitHub Actions ── ビルド → rsync ──→ /srv/gikai/{web,admin} → systemctl restart
```

- **nginx は2段**（ホストの nginx → compose の nginx）。compose はローカル検証と同じものを使い回せる。
  そのかわり、利用者の IP を compose 側に正しく引き継ぐ設定が要る（手順7・手順9）
- 外から届くのは 22 / 80 / 443 だけ。compose のポートと web・admin は `127.0.0.1` でしか待ち受けない

## 4. 手順

**どこで打つコマンドかを取り違えない。** プロンプトで見分ける。

| プロンプト | ここで打つもの |
|---|---|
| 手元（WSL）のプロンプト | `ssh` / `scp` / `rsync`、トンネル、`psql "$PROD_DB_URL"`、`pnpm seed:*`、`gh` |
| `ubuntu@ezocivic-vps1` | `sudo apt`、`sudo htpasswd`、nginx / certbot / systemctl / docker |

（2026-09-29 に `sudo htpasswd` を手元で打って `command not found` になった。htpasswd は VPS にしか入れていない）

### 手順1: コントロールパネルでの作業（人）

1. **OS をインストールする**: サーバー詳細から OS の再インストールを選び、**Ubuntu 24.04 LTS（amd64）** を入れる
   - **「スタートアップスクリプト」は使わない。** 何が入ったか分からなくなるうえ、**選ぶとパケットフィルターが OFF になる**
   - 管理ユーザーのパスワードは長いものにする（SSH では使わないが、コンソールからのログインで使う）
   - **SSH 公開鍵を登録する**（手元の `~/.ssh/id_ed25519.pub`。無ければ `ssh-keygen -t ed25519` で作る）
2. **パケットフィルターを設定する**: 許可するのは **SSH（22）と Web（80 / 443）だけ**
3. インストールが終わるとサーバーは起動する。IPv4 アドレスを控える
4. 契約内容を控えておく: 月額、ゾーン（石狩か東京か）、プランを上げる時にデータが残るか

> **詰まりやすい点: OS を入れ直すとパケットフィルターが 22 番だけに戻る**
>
> パケットフィルターはコントロールパネル側の設定で、**OS の再インストールで引き継がれない**。
> 再インストール直後の既定は 22 番のみ許可なので、そのたびに 80 / 443 を足し直す
> （[さくらのお知らせ](https://vps.sakura.ad.jp/news/vps-pf-vu/)）。忘れると `ufw` で許可していても外から届かず、
> 手順9 の certbot まで進んでから気づくことになる。**手順3 の直後に外から叩いて確かめる。**

> **OS の入れ直しについて（2026-09-27 に VPS が到達不可になり、入れ直した時に調べたこと）**
>
> | 論点 | 結果 | 出典 |
> |---|---|---|
> | 契約し直しが要るか | **不要**。コントロールパネルの操作だけ | [OS再インストール](https://manual.sakura.ad.jp/vps/os-reinstall/reinstall.html) |
> | IP アドレスは変わるか | **変わらない** | [IPアドレスに関するご質問](https://manual.sakura.ad.jp/vps/support/technical/ip-address.html) |
> | ディスクのデータ | **全消去**される | 同上（OS再インストール） |
>
> 入れ直したら、手元の古いホスト鍵を消す: `ssh-keygen -R 153.127.41.244 && ssh-keygen -R ezocivic-vps1`
> （`~/.ssh/config` の `ezocivic-vps1` はそのまま使える）。GitHub Secrets の `VPS_SSH_KNOWN_HOSTS` も取り直す（手順10-3）。

### 手順2: 初回ログインと SSH の締め付け

```bash
# 手元（WSL）から
ssh ubuntu@<IPv4>
```

```bash
# VPS
sudo apt update && sudo apt full-upgrade -y
sudo timedatectl set-timezone Asia/Tokyo
timedatectl            # "System clock synchronized: yes" と "NTP service: active" を確認
sudo hostnamectl set-hostname ezocivic-vps1
```

時刻の同期は必ず確かめる。web のキャッシュの無効化は時計のずれに弱い（検証結果 §4-8）。

SSH をパスワードで入れないようにする:

```bash
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
sudo sshd -t && sudo systemctl reload ssh
```

**今のセッションを閉じずに**、別のターミナルから `ssh ubuntu@<IPv4>` で入れることを確かめてから次に進む。

手元の `~/.ssh/config` に足す:

```
Host ezocivic-vps1
  HostName 153.127.41.244
  User ubuntu
```

### 手順3: ファイアウォールと自動更新

```bash
# VPS
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # Yes
```

再起動が要る更新（カーネル）は自動では再起動しない。月に一度くらい `cat /var/run/reboot-required` を見て、手で再起動する。

> **docker のポートは ufw をすり抜ける。** docker は iptables を直接書き換えるので、compose で `0.0.0.0` に公開したポートは
> ufw で閉じていても外から届く。`infra/compose.yml` は `127.0.0.1` にだけ公開しているので問題ないが、
> ポートを足す時は必ず `127.0.0.1:` を付ける。

> **22 番には常に総当たりが来る。** 立ち上げ直後から、海外の IP が SSH にログインを試み続ける（2026-09-29 に確認）。
> 手順2 で公開鍵認証のみにしてあるので入られることは無いが、ログは汚れる。対策は §8「決めること」。
>
> ```bash
> ss -tn state established '( sport = :22 )'                          # 自分の IP は echo $SSH_CLIENT の先頭
> sudo journalctl -u ssh --since today | grep -c "Invalid user\|Failed"
> ```

### 手順4: スワップ

2GB のメモリに対し、実測は約 1GB 弱（2026-09-30、全部動かした状態で 1.9Gi 中 990Mi）。Next.js の一時的な膨らみに備えて 2GB 足す。

```bash
# VPS
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swap.conf
sudo sysctl --system
free -h
```

### 手順5: Docker・Node.js・rsync を入れる

**Docker Engine**（公式の apt リポジトリ。Ubuntu の `docker.io` パッケージは古いので使わない）:

```bash
# VPS
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker ubuntu     # 入り直すと sudo なしで docker が使える（cron のスクリプトもこれが前提）

sudo tee /etc/docker/daemon.json <<'EOF'
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
EOF
sudo systemctl restart docker
```

**Node.js 22**（web・admin の `server.js` を動かすため。ビルドはしない。CI も 22 に揃えてある）と **rsync**（デプロイの受け側）:

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs rsync
node -v            # v22.x
```

### 手順6: DNS（人）

`ezocivic.tech` は **Xserverドメイン**で取っていて、DNS は Xserverドメインの無料 DNS（`ns1〜3.xdomain.ne.jp`）に置く。
次のレコードを足す。

| ホスト名 | 種別 | 値 |
|---|---|---|
| `gikai` | A | VPS の IPv4 |
| `gikai-admin` | A | VPS の IPv4 |
| `db` | A | VPS の IPv4 |

- IPv6（AAAA）は、nginx を IPv6 でも待ち受けるようにしてから足す。先に AAAA だけ足すと、IPv6 で来た利用者が繋がらない
- `ezocivic.tech`（傘のトップページ）と `studio.` は今回は作らない
- 反映の確認: `nslookup -type=A gikai.ezocivic.tech 8.8.8.8`（手元から）

> **詰まりやすい点: 委任先のネームサーバーにゾーンが無い（2026-09-27 に踏んだ）**
>
> **症状**: `ezocivic.tech` がゾーンごと SERVFAIL で、名前解決が一切できない。レコードの中身は正しい。
>
> **原因**: Xserver にはネームサーバーが2系統あり、ドメインの委任先がゾーンの無い方を向いていた。
>
> | ネームサーバー | 用途 | ゾーンを置く条件 |
> |---|---|---|
> | `ns1〜5.xserver.jp` | エックスサーバー**レンタルサーバー**用 | レンタルサーバーの契約が要る |
> | `ns1〜3.xdomain.ne.jp` | **Xserverドメイン**（ドメイン単体）の無料 DNS | ドメインを持っていれば使える |
>
> **切り分け方**: 委任先のネームサーバーに直接聞く。**REFUSED は「そのゾーンを持っていない」**という応答なので、
> レコードの中身が違うのではなくゾーンごと無いと分かる。
>
> ```bash
> nslookup -type=NS ezocivic.tech ns01.trs-dns.com         # レジストリが持つ委任先
> nslookup -type=A gikai.ezocivic.tech ns1.xdomain.ne.jp   # ゾーンがある側に直接聞く
> ```
>
> **直し方**: Xserverアカウント → ドメイン → `ezocivic.tech` → ネームサーバー設定を
> `ns1.xdomain.ne.jp` / `ns2.xdomain.ne.jp` / `ns3.xdomain.ne.jp` にする。レコードは触らない。

### 手順7: Supabase（compose）を立ち上げる

**1. ファイルを置く**（手元のリポジトリ直下から。develop の最新にしておく）

```bash
ssh -t ezocivic-vps1 'sudo mkdir -p /srv/supabase && sudo chown ubuntu: /srv/supabase'
rsync -av --exclude volumes --exclude .env infra/ ezocivic-vps1:/srv/supabase/
```

> **`ssh` 越しに `sudo` する時は `-t` を付ける。** `ssh host 'command'` は端末を割り当てないので、
> 付けないと `sudo: a terminal is required to read the password` で失敗する。この VPS の `ubuntu` は
> sudo にパスワードが要る（手順10-2）ので、本書の `ssh ... 'sudo ...'` はすべて `-t` 付きにしてある。

**2. 秘密情報を作る**（手元で。**ローカル検証で使った値は使い回さない**）

```bash
openssl rand -hex 32   # JWT_SECRET
openssl rand -hex 24   # POSTGRES_PASSWORD
```

`ANON_KEY` / `SERVICE_ROLE_KEY` は `JWT_SECRET` で署名した HS256 の JWT（有効期限5年）:

```bash
JWT_SECRET=<上で作った値> node -e '
const c = require("node:crypto");
const b64 = (o) => Buffer.from(JSON.stringify(o)).toString("base64url");
const now = Math.floor(Date.now() / 1000);
for (const role of ["anon", "service_role"]) {
  const h = b64({ alg: "HS256", typ: "JWT" });
  const p = b64({ role, iss: "supabase", iat: now, exp: now + 5 * 365 * 86400 });
  const s = c.createHmac("sha256", process.env.JWT_SECRET).update(`${h}.${p}`).digest("base64url");
  console.log(`${role}: ${h}.${p}.${s}`);
}'
```

> **詰まりやすい点: トンネル（2026-09-29 に実際に踏んだもの）**
>
> - **オプションを省かない。** keepalive が無いと、WSL のスリープや NAT のタイムアウトで TCP が**半死**になる。
>   ssh のプロセスは生きていてローカルのポートも待ち受け続けるので、一見正常なのに接続だけがタイムアウトする。
>   `ServerAliveInterval=30` で90秒で検知して終了し、`ExitOnForwardFailure=yes` でポートを掴めなかった時に黙って動き続けるのを防ぐ
> - **5433 と 8000 は別々に死ぬ。** `psql` が通ることは 8000 が生きている根拠にならない。
>   `seed:master` が `TypeError: fetch failed` で落ちたら 8000 を疑い、上の `curl` を見る。
>   VPS 側が生きているかは `ssh ezocivic-vps1 'curl -s 127.0.0.1:8000/auth/v1/health'` で切り分ける
> - **TCP が繋がるだけでは判断できない。** ssh はリモートに届かなくてもローカルの接続は受け付ける。上の `psql` / `curl` で確かめる
> - **張り直す前に `pgrep -af "ssh .*-L"` で今あるものを見る。** 生きている方まで止めたり、二重に張ったりしやすい
>   （`-f` 付きで2回張ると2回目は `Address already in use` で失敗する。1回目が生きているので害は無い）
> - **シェルの履歴から古い形のコマンドを呼ばない。** keepalive 無しで張り直すことになる
> - **local 側に `127.0.0.1:` を付ける。** 省くと WSL では `bind [::1]:5433: Cannot assign requested address` が出る（無害だが紛らわしい）
> - **`-N` はプロンプトを返さない**（固まったのではない）。`-f` で背景に回る。付け忘れたら `Ctrl+Z` → `bg`

> **詰まりやすい点: `export` はターミナルごと**
>
> 別のターミナルには引き継がれない。空のまま実行すると、紛らわしいエラーになる。
>
> | 症状 | 原因 |
> |---|---|
> | `psql`: `connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed` | `PROD_DB_URL` が空（手元の Unix ソケットに繋ごうとした） |
> | `psql`: `127.0.0.1, port 5433 ... Connection refused` | トンネルが落ちている |
> | `supabase migration up`: `failed to connect to host=127.0.0.1` | `--db-url ""`（`PROD_DB_URL` が空） |
> | curl: `401 no_authorization`（`This endpoint requires a valid Bearer token`） | `SUPABASE_SERVICE_ROLE_KEY` が空 |

### 手順9: ホストの nginx と TLS

**1. 入れる**

```bash
# VPS
sudo apt install -y nginx certbot python3-certbot-nginx apache2-utils
```

**2. vhost を置く**。**apt で入る `default` サイトは先に外す**（下の「詰まりやすい点」）。
代わりに、どの vhost にも当たらない通信（IP 直打ちなど）を黙って切る受け皿を置く。

```bash
# VPS。3つの vhost は手順7 の rsync で /srv/supabase/host-nginx/ に届いている
sudo rm /etc/nginx/sites-enabled/default
sudo tee /etc/nginx/sites-available/00-default.conf > /dev/null <<'EOF'
server {
  listen 80 default_server;
  server_name _;
  return 444;
}
EOF
sudo ln -sfn /etc/nginx/sites-available/00-default.conf /etc/nginx/sites-enabled/00-default.conf

for f in gikai.ezocivic.tech.conf gikai-admin.ezocivic.tech.conf db.ezocivic.tech.conf; do
  sudo cp "/srv/supabase/host-nginx/$f" /etc/nginx/sites-available/
  sudo ln -sfn "/etc/nginx/sites-available/$f" "/etc/nginx/sites-enabled/$f"
done
ls /etc/nginx/sites-enabled/   # 00-default.conf と 3 つの vhost だけ（default が無いこと）
```

vhost の要点:

- `gikai` → `127.0.0.1:3004`、`gikai-admin` → `127.0.0.1:3003`、`db` → `127.0.0.1:8000`
- 3つとも `X-Real-IP $remote_addr` と `X-Forwarded-For $remote_addr`（利用者が送った値を**上書き**する）、`X-Forwarded-Proto $scheme`
- web・admin は AI の応答をストリーミングで返すので `proxy_buffering off;`。`db` は `client_max_body_size 50m;`（サムネイル）
- **公開前は `gikai` と `gikai-admin` に Basic 認証をかける**。`db` にはかけない

**3. Basic 認証のパスワードファイルを作る**（web と admin で別のファイル。片方だけパスワードを変えられるように）

| vhost | パスワードファイル |
|---|---|
| `gikai.ezocivic.tech` | `/etc/nginx/htpasswd-gikai-web` |
| `gikai-admin.ezocivic.tech` | `/etc/nginx/htpasswd-gikai` |

```bash
# VPS。パスワードは対話で2回打つ
sudo htpasswd -c /etc/nginx/htpasswd-gikai-web <ユーザー名>
sudo htpasswd -c /etc/nginx/htpasswd-gikai     <ユーザー名>
sudo cat /etc/nginx/htpasswd-gikai-web /etc/nginx/htpasswd-gikai   # それぞれ「ユーザー名:$apr1$...」の行があること
```

決めたユーザー名とパスワードは**パスワードマネージャーに保存する**（ファイルにはハッシュしか残らない）。

- なぜ nginx でかけるか: アプリにも Basic 認証（`BASIC_AUTH_USER` など）はあるが、web のものは画面（HTML）にしか効かず、
  `/api/chat` などは素通しになる（`web/src/middleware.ts` の `_isHtmlRequest`）。nginx なら server ブロック全体に効く
- なぜ `db` にかけないか: ブラウザの supabase-js は別オリジンの API に認証情報を付けないので、かけると画面から Supabase を呼べなくなる。
  `db` は RLS（ポリシー無し＝全拒否）で守られていて、anon キーでは何も読めない
- 全パスにかけると、アプリが**自分の公開 URL を叩く通信**も 401 になる。admin → web の revalidate と admin のトピック分析がそれで、
  内部宛ての環境変数（`WEB_INTERNAL_URL` / `ADMIN_INTERNAL_URL`）で逃がしてある（手順10-1）

> **詰まりやすい点: htpasswd が空ファイルになる**（2026-09-29 に踏んだ）
>
> 2回目の確認入力が1回目と一致しないと `htpasswd: password verification error` で終わるが、`-c` はファイルを先に作るので
> **0 バイトのファイルだけが残る**。もう一度 `-c` 付きで流し、`sudo cat` で行があるか確かめる。
> 合っているかは `sudo htpasswd -v <ファイル> <ユーザー名>` で確かめられる。

**5. 転送ループが無いか確かめる**

```bash
# VPS。3つとも 1 なら正常（80 番のブロックにだけある）
grep -c "return 301" /etc/nginx/sites-available/*.ezocivic.tech.conf

# 手元
curl -s https://db.ezocivic.tech/auth/v1/health                                # GoTrue の JSON
curl -s -o /dev/null -w "%{http_code}\n" https://gikai.ezocivic.tech/          # 401（Basic 認証）
curl -s -o /dev/null -w "%{http_code}\n" https://gikai-admin.ezocivic.tech/    # 401
curl -s -o /dev/null -w "%{http_code}\n" http://gikai.ezocivic.tech/           # 301（https へ）
```

> **詰まりやすい点: certbot が `default` に書き込む**（2026-09-29 に踏んだ）
>
> **症状**: `https://gikai.ezocivic.tech/` が 200（nginx の Welcome ページ）、`https://db.ezocivic.tech/auth/v1/health` が 404。
>
> **原因**: vhost を置く前に certbot を流していて、証明書と 443 番の server ブロックが `default` に書き込まれた。
> あとから置いた vhost は 80 番しか待ち受けていなかった。
>
> **直し方**: `default` を外し、`00-default.conf` を置いてから certbot を流し直す。
> 「1: Attempt to reinstall this existing certificate」を選ぶ（取り直さないので、Let's Encrypt の発行回数の制限を使わない）。
> **certbot は必ず vhost を置いた後に流す。**

> **詰まりやすい点: https でも 301 が返り続ける**（2026-09-29 に db と gikai で起きた。gikai-admin は正常だった）
>
> certbot の reinstall で、80 番用の `if ($host = ...) { return 301 https://...; }` が **443 番の server ブロックにも**入った。
> 上の `grep -c` が 2 になるファイルの、443 番側の `if` ブロック（3行）を手で消す。
>
> **一括で直さない。** 3つすべてに「最初の `if` ブロックを消す」操作をかけたところ、正常だった gikai-admin の
> 残すべき 80 番の転送まで消してしまった。直す前にファイルごとに `grep -n "server {\|if (\$host\|listen"` で構造を見て、
> `sudo cp <ファイル> <ファイル>.bak` で退避してから触る。

> **設置した後の vhost はコピーし直さない。** `sites-available/` の vhost には certbot が TLS の行を書き足しているので、
> `/srv/supabase/host-nginx/` からコピーし直すと TLS の設定が消える。直す時は置いてあるファイルを `sed -i` で直す（§5）。

```bash
chmod 600 /srv/gikai/web.env /srv/gikai/admin.env
```

`SUPABASE_SERVICE_ROLE_KEY` などは `/srv/supabase/.env` にある値を使う（`grep` で読めば手で打つのは `OPENAI_API_KEY` だけで済む）。

| 変数 | web | admin | 備考 |
|---|---|---|---|
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | ○ | ○ | `createAdminClient()` が読む |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ○ | ○ | **ビルド時にも必要** |
| `NEXT_PUBLIC_WEB_URL` | ○ | ○ | ビルド時にも必要 |
| `NEXT_PUBLIC_APP_URL` | ✕ | ○ | web は読まない |
| `ADMIN_URL` | ○ | ✕ | プレビュー画面から管理画面へ戻るリンク。未設定だと `http://localhost:3001` |
| `ADMIN_INTERNAL_URL` | ✕ | ○ | トピック分析が admin 自身を呼ぶ宛先（PR #56）。**無いと Basic 認証で 401** |
| `WEB_INTERNAL_URL` | ✕ | ○ | admin → web の `/api/revalidate` の宛先（PR #51）。**無いと Basic 認証で 401** |
| `REVALIDATE_SECRET` | ○ | ○ | 両方に同じ値 |
| `OPENAI_API_KEY` | ○ | ○ | AI SDK が直接読む |
| `AI_GLOBAL_DAILY_COST_LIMIT_USD` / `CHAT_…` / `INTERVIEW_…` | ○ | ✕ | 公開前は 1 / 0.5 / 0.5。未設定なら 5 / 0.5 / 0.5 |
| `PORT` / `HOSTNAME` / `NODE_ENV` | ○ | ○ | standalone の `server.js` が読む |
| `BASIC_AUTH_*` / `ADMIN_BASIC_AUTH_*` | | | **設定しない**（Basic 認証は nginx でかける） |
| `ADMIN_ENABLE_CLAUDE_CLI` / `CLAUDE_CLI_PATH` | | | **設定しない**（Claude CLI を使う機能はローカル専用） |

**`NEXT_PUBLIC_*` はビルド時に JS へ埋め込まれる。** env ファイルだけ直してもブラウザ側には反映されない。
値を変えたら 10-3 の GitHub Variables も直して、デプロイをやり直す。

**10-2. systemd unit と sudoers**（手元から送って VPS で置く）

```bash
# 手元（リポジトリ直下）
scp infra/systemd/gikai-web.service infra/systemd/gikai-admin.service infra/sudoers/gikai-deploy ezocivic-vps1:/tmp/

# VPS（sudo のパスワードを聞かれるので -t）
ssh -t ezocivic-vps1 '
sudo install -o root -g root -m 0644 /tmp/gikai-web.service /tmp/gikai-admin.service /etc/systemd/system/ &&
sudo install -o root -g root -m 0440 /tmp/gikai-deploy /etc/sudoers.d/gikai-deploy &&
sudo visudo -cf /etc/sudoers.d/gikai-deploy &&
sudo systemctl daemon-reload &&
sudo systemctl enable gikai-web gikai-admin &&
rm /tmp/gikai-web.service /tmp/gikai-admin.service /tmp/gikai-deploy'

ssh ezocivic-vps1 'sudo -n -l'   # (root) NOPASSWD: /usr/bin/systemctl restart gikai-web gikai-admin の1行だけが出れば正しい
```

- **`visudo -cf` は省かない。** sudoers を壊すと sudo が使えなくなる
- まだ `server.js` が無いので `enable` だけにする（`--now` を付けると `Cannot find module '/srv/gikai/web/web/server.js'` で失敗する）。
  最初の起動は 10-4 のデプロイが行う
- unit の要点: `User=ubuntu`、`WorkingDirectory=/srv/gikai/web/web`（モノレポの standalone は一段深い）、
  `EnvironmentFile=/srv/gikai/web.env`、`ExecStart=/usr/bin/node server.js`、`MemoryHigh=450M` / `MemoryMax=600M`
  （超えると SIGKILL。落ちるなら env に `NODE_OPTIONS=--max-old-space-size=400` を足す）
- sudoers は `ubuntu ALL=(root) NOPASSWD: /usr/bin/systemctl restart gikai-web gikai-admin` の1行だけ。
  引数まで含めて突き合わせるので、片方だけの再起動は含まれない

> **sudoers は実際に効く**（2026-09-27 に実機で確認し、当初の誤った前提を訂正した）
>
> クラウドイメージでよくある `/etc/sudoers.d/90-cloud-init-users`（`ubuntu ALL=(ALL) NOPASSWD:ALL`）は、
> さくらのVPS の Ubuntu 24.04 標準OSインストールには**無い**（`/etc/sudoers.d/` には `README` のみ）。
> そのため `ubuntu` の sudo は既定でパスワードを要求し、このファイルを置くとデプロイ鍵で通るのは restart だけになる。
> 裏返すと、**このファイルを置くまでデプロイは restart で必ず失敗する**。別のイメージや VPS に移す時は `sudo -n -l` で前提を確かめる。

**10-3. デプロイ用の鍵と GitHub の登録**（人、手元）

```bash
# デプロイ専用の鍵（普段使いの鍵は使わない）
ssh-keygen -t ed25519 -C "github-actions-gikai-deploy" -f ~/.ssh/gikai_deploy -N ""
ssh-copy-id -i ~/.ssh/gikai_deploy.pub ezocivic-vps1
ssh -i ~/.ssh/gikai_deploy ubuntu@153.127.41.244 'echo ok'

R=s-takahashi-hokkaido/dejimin-gikai

# Variables（秘密ではない値。anon キーはブラウザに配られる値なので Variables でよい）
gh variable set VPS_HOST -R $R --body "gikai.ezocivic.tech"
gh variable set VPS_USER -R $R --body "ubuntu"
gh variable set NEXT_PUBLIC_SUPABASE_URL -R $R --body "https://db.ezocivic.tech"
gh variable set NEXT_PUBLIC_SUPABASE_ANON_KEY -R $R --body "<手順7 の ANON_KEY>"
gh variable set NEXT_PUBLIC_WEB_URL -R $R --body "https://gikai.ezocivic.tech"
gh variable set NEXT_PUBLIC_APP_URL -R $R --body "https://gikai-admin.ezocivic.tech"
# SSH のポートを 22 から変えた時だけ: gh variable set VPS_SSH_PORT -R $R --body "<port>"

# Secrets
gh secret set VPS_SSH_PRIVATE_KEY -R $R < ~/.ssh/gikai_deploy
ssh-keyscan -t ed25519 gikai.ezocivic.tech | gh secret set VPS_SSH_KNOWN_HOSTS -R $R

gh variable list -R $R && gh secret list -R $R   # Variables 6件・Secrets 2件
```

- **`-R` を付ける。** このリポジトリはリモートが3つ（origin / upstream / team-mirai）あるので、付けないと
  `multiple remotes detected` で止まるか、別のリポジトリに登録してしまう
- **repository レベルに登録する。** リポジトリには Environment（Preview / Production）もあるが、`deploy_vps.yml` は
  `environment:` を指定していないので、Environment に登録した値は読まれない
- **`known_hosts` は `VPS_HOST` と同じ名前で取る。** IP で取って名前で接続すると照合に失敗する。
  SSH のポートを変えている場合は `ssh-keyscan -p <port>` で取る
- anon キーの取り違え（service_role を入れていないか）は、JWT の真ん中を base64 で戻して `"role":"anon"` かで確かめられる
- **GitHub に置かないもの**: `SUPABASE_SERVICE_ROLE_KEY` / `OPENAI_API_KEY` / `REVALIDATE_SECRET` / DB のパスワード / `JWT_SECRET`。
  ビルドは DB に接続しないので要らない

**10-4. デプロイする**

```bash
gh workflow run "Deploy VPS" -R s-takahashi-hokkaido/dejimin-gikai --ref develop
gh run watch -R s-takahashi-hokkaido/dejimin-gikai
```

（GitHub の画面からは Actions → Deploy VPS → Run workflow。ブランチは `develop` か `main` しか受け付けない）

ワークフローの中身:

1. 実行したブランチと、Variables / Secrets の登録漏れを確かめる（漏れていればビルド前に止まる）
2. `pnpm install --frozen-lockfile` → `pnpm --filter web build` / `pnpm --filter admin build`（Variables の `NEXT_PUBLIC_*` を渡す）
3. `.next/standalone` に `.next/static` と `public` をコピー
4. `rsync -az --delete` で `/srv/gikai/web/` と `/srv/gikai/admin/` に送る
5. `sudo systemctl restart gikai-web gikai-admin`
6. VPS 内から web・admin を叩いて 2xx / 3xx を確かめる。成功すると
   `gikai-web OK (127.0.0.1:3004 -> 200)` / `gikai-admin OK (127.0.0.1:3003 -> 307)`（admin はログインへの転送）

初回だけ、デプロイの後に起動状態を確かめる:

```bash
ssh ezocivic-vps1 'systemctl status gikai-web gikai-admin --no-pager | head -20'   # active (running)
```

**デプロイがうまくいかない時**（失敗したステップのログは `gh run view <run-id> -R $R --log-failed | tail -30`。
画面の Annotations には `exit code 1` としか出ず、`Node.js 20 is deprecated` などの警告は原因ではない）

| 症状 | 原因と直し方 |
|---|---|
| 20秒足らずで失敗。ログに `GitHub に登録されていません: VPS_HOST ...` | 10-3 の登録漏れ。repository レベルに登録したか |
| `デプロイできるのは develop / main だけです` | `--ref` の指定違い |
| `Host key verification failed` | `VPS_SSH_KNOWN_HOSTS` を `VPS_HOST` と同じ名前で取り直す。OS を入れ直した後も取り直す |
| rsync が `Permission denied` | `/srv/gikai/{web,admin}` の所有者が `ubuntu` か。デプロイ鍵が `authorized_keys` にあるか |
| `Restart services` で `sudo: a password is required` | 10-2 の sudoers が無い（ビルドと rsync は済んでいる）。10-2 を済ませて再実行 |
| `Verify services are up` で失敗 | `journalctl -u gikai-web -n 50`。env ファイルの権限、`/srv/gikai/web/web/server.js` の有無、unit が `enable` されているか |

### 手順11: 定期処理（cron）

**まだ済んでいない。バックアップが1度も取られていないので、先に済ませる。**

| 時刻 | 処理 | 中身 |
|---|---|---|
| 毎日 3:00 | バックアップ（`backup.sh`） | `/srv/backups/<YYYYMMDD>/` に `migrations.txt` / `data.sql` / `storage.tar` を取り、14日より古いものを消す |
| 毎日 3:30 | 会話ログの削除（`delete-expired-chat-logs.sh`） | 90日を過ぎた AI チャットの会話ログを消す（`public.delete_expired_chat_logs()`） |

```bash
# VPS。スクリプトと cron の定義は手順7 の rsync で /srv/supabase/{scripts,cron}/ に届いている
sudo mkdir -p /srv/backups
sudo chown ubuntu: /srv/backups
sudo chmod 700 /srv/backups
sudo install -o root -g root -m 644 /srv/supabase/cron/gikai /etc/cron.d/gikai

# cron を待たずに1回流して確かめる（backup.sh は初回だけ ubuntu:24.04 イメージの pull が走る）
/srv/supabase/scripts/backup.sh
/srv/supabase/scripts/delete-expired-chat-logs.sh
ls -la /srv/backups/"$(date +%Y%m%d)"
```

- ログは journald に入る: `journalctl -t gikai-backup -n 50` / `journalctl -t gikai-chat-logs -n 50`
- `backup.sh` が毎回出す `pg_dump: warning: there are circular foreign-key constraints`（`prompts` と `prompt_versions`）は正常
- **`chat_logs` はバックアップに入れない。** 入れると DB から90日で消した会話ログがバックアップに最大14日生き延び、
  プライバシーポリシーの「90日で自動的に削除」と食い違う。復元しても会話ログは戻らない（分析用の一時データなので戻せなくてよい）
- `/srv/backups` には市民のインタビュー回答・利用者のメールアドレスとパスワードハッシュが入る。700 のまま、持ち出す時も置き場所に気をつける
- **VPS の中にだけ置いても、VPS が壊れたら一緒に失う。** 持ち出し先は §8「決めること」
- 復元の手順は [infra/scripts/README.md](../infra/scripts/README.md)「復元」。練習は手元の compose に対して行う

## 5. 日常の運用

### デプロイ

develop に取り込んだ変更は、10-4 のワークフローを手動で実行すれば VPS に反映される。

- `rsync --delete` は動いているプロセスの下でファイルを差し替えるので、**転送中にまだ読まれていないページへアクセスすると 500 になることがある**
- `--delete` なので**前の版は VPS に残らない。** 戻したい時は、戻したいコミットを develop に入れてデプロイし直す
- develop への push で自動デプロイにするなら、`deploy_vps.yml` の先頭にコメントで残してある `push:` を有効にする（公開後に判断）

### `infra/` を直した時

VPS には `rsync -av --exclude volumes --exclude .env infra/ ezocivic-vps1:/srv/supabase/` で配り直す。VPS 上で直接編集しない。
ただし `/etc/` にコピー済みのものは配っただけでは変わらないので、それぞれ置き直す:

| 直したもの | 反映のしかた |
|---|---|
| `compose.yml` / `nginx/supabase.conf` | `cd /srv/supabase && docker compose up -d` |
| `host-nginx/*.conf` | **コピーし直さない**（certbot の TLS の行が消える）。`/etc/nginx/sites-available/` のファイルを `sed -i` で同じように直し、`sudo nginx -t && sudo systemctl reload nginx` |
| `systemd/*.service` | 手順10-2 と同じく置き直し、`sudo systemctl daemon-reload` の後に restart |
| `cron/gikai` | 手順11 の `install` をやり直す |

### DB を触る

手順8 のトンネルと `export` をしてから `psql "$PROD_DB_URL"`。**本番 DB なので、書き込む前に接続先を確かめる。**

### Basic 認証のユーザー名・パスワード

```bash
# ユーザー名を見る
ssh ezocivic-vps1 'sudo cut -d: -f1 /etc/nginx/htpasswd-gikai-web /etc/nginx/htpasswd-gikai'

# パスワードを変える・忘れた時に付け直す（-c を付けない。-c はファイルを作り直して他のユーザーを消す）
ssh -t ezocivic-vps1 'sudo htpasswd /etc/nginx/htpasswd-gikai-web <ユーザー名>'   # web だけ
ssh -t ezocivic-vps1 'sudo htpasswd /etc/nginx/htpasswd-gikai <ユーザー名>'       # admin だけ

# 確かめる（手元）
curl -s -o /dev/null -w "%{http_code}\n" -u '<ユーザー名>:<パスワード>' https://gikai.ezocivic.tech/   # 200
```

nginx の reload は要らない（次のリクエストから効く）。

### 議案データを流し直す

第3回定例会の会期後などは、`packages/seed/main/sapporo-bills/` を直して手順8-5 の `pnpm seed:bills` を流し直す。
流し直した後は web のキャッシュを無効にする（手順8-5 の最後）。

|---|---|
| **T1 名称の商標** | 調査済み・判断待ち。**これが付くまで公開しない** |
| **`SERVICE_ROLE_KEY` を作り直すか** | 立ち上げ作業中に、本番の `SERVICE_ROLE_KEY` がチャットのログや画面に出た。キーは `JWT_SECRET` で署名した JWT なので、無効にするには `JWT_SECRET` から作り直す。その場合は `ANON_KEY` も作り直し、`/srv/supabase/.env`・`web.env` / `admin.env`・GitHub Variables（`NEXT_PUBLIC_SUPABASE_ANON_KEY`）をすべて差し替えてデプロイし直す |
| **SSH への総当たり対策** | (a) パケットフィルターで 22 番の接続元を自分の IP に限定（一番効くが、IP が変わると自分も入れなくなる）、(b) `fail2ban`（IP が変わっても困らない）、(c) 何もしない（実害は無い）。**(a) か (b) を決める** |
| バックアップの持ち出し先 | (a) 手元の WSL から毎日 `rsync` で取りに行く（無料。手元の PC が点いている時しか取れない）、(b) さくらのオブジェクトストレージ（月額が掛かる、国内のまま）。**まずは (a)**、公開後に (b) を検討 |
| サーバーログの保存期間と閲覧者 | journald の保存期間（例: `SystemMaxRetentionSec=30d`）。LLM のエラー時に市民の発言がログに出るため。決めたらプライバシーポリシー第8条に足す |
| IPv6 | vhost に `listen [::]:80` をコメントで残してある。有効にするなら3つの vhost と DNS の AAAA を同時に。足さなくても IPv4 で繋がる |
| 管理者パスワードの最低文字数 | 今は 6（`GOTRUE_PASSWORD_MIN_LENGTH`）。議員に開放する前に見直す（T10） |
| Storage を残すか | 今は storage-api を載せている。nginx の静的配信に替えると約 116MiB 減る。メモリが苦しくなったら検討 |

### 公開後の宿題（今は直さない）

| 論点 | 内容 |
|---|---|
| `rsync --delete` の副作用 | 転送中に一時的に 500 が出うる／前の版が残らず自動ロールバックできない。リリースごとのディレクトリ＋symlink 切り替えが素直 |
| デプロイ専用ユーザー | sudoers は効いているので優先度は低い。作るなら公開鍵をそのユーザーに置き、sudoers の1行目・`/srv/gikai` の所有者・unit の `User=` を合わせる |
| CI で `next build` を流していない | ビルドが壊れてもデプロイ実行時まで気づかない。CI 時間とのトレードオフで現状維持 |
| `factions` / `committees` に `name` の unique 制約が無い | `seed:master` は既存行を読んでキーで突き合わせている。制約を足せば簡単になるが、マイグレーションと既存データの確認が要るので別 PR |
| マスタ投入の integration テストが無い | `seed:master` の書き込み経路は使い捨てスタックでの手動検証のみ |
