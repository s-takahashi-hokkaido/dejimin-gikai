# 公開までのタスク分割（複数セッション並行用）

- 作成: 2026-09-23
- 目的: [プロジェクト方針とやりたいこと整理](20260912_1528_プロジェクト方針とやりたいこと整理.md) §10 の残作業を、**1タスク＝1セッション（＝1 worktree・1 PR）**の単位に切り分ける。セッションを並べて同時に進めるときに、衝突しない組み合わせが一目でわかるようにする
- 位置づけ: 何をやるか・なぜやるかの正本は方針ドキュメントのまま。このドキュメントは「どう分けて進めるか」だけを持つ

---

## 0. 使い方

### セッションの始め方

新しいセッションには次のように頼む。

> `docs/20260923_1740_公開までのタスク分割.md` のタスク **T3** をやって

そのセッションは次の順で進める。

1. このドキュメントの該当タスクと、「読むもの」に挙げたドキュメントを読む
2. 「先に決めること」が残っていたら、**着手前にユーザーへ確認する**
3. CLAUDE.md の手順どおり worktree を作る（ブランチ名は各タスクの「ブランチ」欄）
4. 作業 → `pnpm lint` / `pnpm typecheck` / `pnpm test` → PR（base は `develop`）→ `/review`
5. **同じ PR の中で、このドキュメントの該当タスクの「状態」行を更新する**

### 状態の書き方

各タスクの PR では、そのタスクの「状態」行（§2）だけを書き換える。§進捗 の表は書き換えない。
表を各 PR で触ると、隣り合う行を同時に書き換えてコンフリクトするため。

- `未着手` / `進行中（PR #xx）` / `完了（PR #xx, YYYY-MM-DD）` / `保留（理由）`

§進捗 の表は**棚卸しの時だけ**まとめて更新する。棚卸しは「タスク分割の棚卸しをして」と頼む。
棚卸しでは「状態」行を鵜呑みにせず、PR の状態（`gh pr list --state all`）とコードの実物を見て判定し、ずれていれば「状態」行も直す。

### 人手が要るタスク

「種類」が **人** のタスクは、契約・相談・目視確認など Claude だけでは完結しないもの。Claude は下調べと手順書づくりまで担当する。

### T11. AI コストガードの仕上げ

- 状態: 完了（PR #TBD, 2026-09-24）

- 読むもの: 方針ドキュメント §7
- 決めたこと:
  - **fail-open は維持する**。判定が失敗してアプリ側の上限が外れても、OpenAI 側の予算上限が最後の歯止めになる
  - **通知は作らない**。OpenAI の予算通知メールで足りる
- UI で確認したこと（チャット・インタビューの両方）:
  - アプリ側の上限到達（429）: 「本日の利用上限に達しました。明日0時以降に再度お試しください。」と出る。問題なし
  - OpenAI 側の拒否（`insufficient_quota`）: 修正前はチャットに OpenAI の英語のエラー文（請求情報の案内を含む）、インタビューに `Failed to fetch` が出ていた。汎用の文面「エラーが発生しました。しばらく待ってから再度お試しください。」に置き換えた
  - インタビューの初回質問（`generateInitialQuestion`）が上限の対象外で、利用額の記録もしていなかった。上限判定と記録を足した
- 残り（人）: OpenAI 側の予算上限が「超えたらリクエストを拒否する」設定になっているかを管理画面で確かめる。通知だけの設定なら、アプリ側の上限が唯一の歯止めになるので fail-open を見直す
