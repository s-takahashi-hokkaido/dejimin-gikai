## 3. 詰まったところ

### 3-1. Variables / Secrets の登録漏れ（1回目の失敗）

GitHub の画面には `Process completed with exit code 1.` としか出ない。ログの
`Check deploy ref, variables and secrets` ステップに原因が出ている:

```
GitHub に登録されていません: VPS_HOST VPS_USER NEXT_PUBLIC_SUPABASE_URL NEXT_PUBLIC_SUPABASE_ANON_KEY NEXT_PUBLIC_WEB_URL NEXT_PUBLIC_APP_URL VPS_SSH_PRIVATE_KEY VPS_SSH_KNOWN_HOSTS
```

画面の Annotations に出る警告（`Node.js 20 is deprecated` / `ubuntu-latest label will migrate to Ubuntu 26`）は
失敗の原因ではない。ログは手元から次で見られる:

```bash
gh run view <run-id> -R s-takahashi-hokkaido/dejimin-gikai --log-failed | tail -30
```

注意点:

- **repository レベルに登録する。** リポジトリには Environment（Preview / Production）もあるが、
  `deploy_vps.yml` は `environment:` を指定していないので、Environment に登録した値は読まれない
- **`gh` は `-R` を付ける。** このリポジトリはリモートが3つ（origin / upstream / team-mirai）あるので、
  `gh secret list` などは `multiple remotes detected` で止まる。
  `-R s-takahashi-hokkaido/dejimin-gikai` を付ければ確実（付けずに upstream へ登録してしまう事故も防げる）

### 3-2. `sudo: a password is required`（2回目の失敗）

rsync までは成功し、最後の `sudo systemctl restart gikai-web gikai-admin` で失敗した。
**systemd unit と sudoers（`/etc/sudoers.d/gikai-deploy`）がまだ置かれていなかった**ため。

- 手順書は「10-2 最初のデプロイ」→「10-3 systemd unit」の順に書かれているが、
  **ワークフローは最後に restart するので、unit と sudoers は最初のデプロイより前に要る**
  （infra/README.md §2-3 → §4 の順が正しい）
- infra/README.md §2-3 は「VPS にリポジトリを clone してある」前提で書かれていたが、
  手順書の方針は **VPS にリポジトリを置かない**。この日は手元から `scp` で送って設置した:

```bash
# 手元（リポジトリ直下）
scp infra/systemd/gikai-web.service infra/systemd/gikai-admin.service infra/sudoers/gikai-deploy ezocivic-vps1:/tmp/

# VPS（sudo のパスワードを聞かれるので -t）
ssh -t ezocivic-vps1 '
sudo install -o root -g root -m 0644 /tmp/gikai-web.service /tmp/gikai-admin.service /etc/systemd/system/ &&
sudo install -o root -g root -m 0440 /tmp/gikai-deploy /etc/sudoers.d/gikai-deploy &&
sudo visudo -cf /etc/sudoers.d/gikai-deploy &&
sudo systemctl daemon-reload &&
sudo systemctl enable --now gikai-web gikai-admin &&
rm /tmp/gikai-web.service /tmp/gikai-admin.service /tmp/gikai-deploy'
```

失敗した回でも rsync は済んでいて `server.js` が届いていたので、ここで `--now` を付けて起動まで行えた
（`server.js` が無い状態で `--now` を付けると `Cannot find module` で失敗する。infra/README.md §2-3）。

### 3-3. Basic 認証のユーザー名・パスワードがどこにも無い

リポジトリには書いていない（書かない）。手順9 で `htpasswd` を流した人がその場で決めたもの。

- ユーザー名は VPS で見られる: `ssh ezocivic-vps1 'sudo cut -d: -f1 /etc/nginx/htpasswd-gikai'`
- パスワードはハッシュしか残らないので **取り出せない**。忘れたら `-c` を付けずに `htpasswd` で上書きする
  （`-c` はファイルを作り直すので他のユーザーが消える）。reload は不要
- **決めたらパスワードマネージャーに保存する**

### 3-4. web だけパスワードを変えたい

もともと2つの vhost が同じ `/etc/nginx/htpasswd-gikai` を見ていたので、片方だけは変えられなかった。
web 用のファイルを新しく作り、`gikai` の vhost だけ参照先を変えた:

```bash
ssh -t ezocivic-vps1 'sudo htpasswd -c /etc/nginx/htpasswd-gikai-web <ユーザー名>'

ssh -t ezocivic-vps1 '
sudo sed -i "s#auth_basic_user_file /etc/nginx/htpasswd-gikai;#auth_basic_user_file /etc/nginx/htpasswd-gikai-web;#" /etc/nginx/sites-available/gikai.ezocivic.tech.conf &&
grep -n auth_basic /etc/nginx/sites-available/gikai.ezocivic.tech.conf &&
sudo nginx -t && sudo systemctl reload nginx'
```

`sites-available/` の vhost は certbot が TLS の行を書き足しているので、`/srv/supabase/host-nginx/` から
**コピーし直すと TLS の設定が消える**。置いてあるファイルを `sed -i` で直す。
