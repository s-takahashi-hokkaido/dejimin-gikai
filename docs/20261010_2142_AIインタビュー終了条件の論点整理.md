# AIインタビュー終了条件の論点整理

## 背景

AIインタビューで、AI側からなかなか「終了しますか？」という流れにならず、深掘りが続いてしまう。
本ドキュメントでは現状の仕組みと原因を整理し、終了条件の設計について検討すべき論点と選択肢を挙げる。
**結論はまだ出さない**（方針を決めてから実装 Issue / PR に落とす）。

## 現状の仕組み

### ステージ遷移

- インタビューは `chat` → `summary` → `summary_complete` の3ステージ
- チャットLLMが毎ターン構造化出力で `next_stage` を返し、それがそのままステージになる（ファシリテーターLLMは国政版 #404 で廃止済み）
- `chat` 中に `next_stage = "summary"` が返ると、クライアントが**確認なしで自動的に**要約リクエストを送る
  - `web/src/features/interview-session/client/hooks/use-interview-chat.ts`（`next_stage === "summary" && stageRef.current === "chat"` の分岐）
- ユーザーが自分で終える手段として、終了ボタン（`use-end-interview.ts`）がある

### 終了判定に関わるプロンプト

`web/src/features/interview-session/shared/utils/` 配下。

| 箇所 | 内容 |
|---|---|
| `stage-transition-guidance.ts`（bulk） | 事前定義質問が残っていれば必ず `chat`／全問完了後も深掘りが十分でなければ `chat`／全問完了かつ十分な深掘り後に初めて `summary` を検討／ユーザーが終了を希望したら `summary` |
| `stage-transition-guidance.ts`（loop） | 事前定義質問を概ね完了し十分な深掘りをしたら `summary` を検討／ユーザー希望時・これ以上深掘りが難しい時も `summary` |
| `bulk-mode.ts` / `loop-mode.ts` の「事前定義質問の活用ルール」 | 終了判定は「全問終了かつ十分な深掘り完了」か「ユーザーの終了意思表示」。最後に「これまでの内容をまとめ、レポートを作成します」と案内する |
| `bulk-mode.ts` の「移行の合図」 | 全問完了後に「ここからは、特に気になった点について深くお伺いしていきます」と宣言して深掘りフェーズに入る |
| `buildTimeManagementGuidance` | `estimated_duration` 設定時のみ有効。超過時も「ユーザーがレポート作成に進みたいと**言った場合は** `summary`」と受け身 |

## 原因の整理

1. **「終了しますか？」と確認する仕組みが存在しない**
   - プロンプトに「ユーザーへ終了を確認する」指示がない。遷移は LLM が `summary` を出すか出さないかの二択で、出した瞬間に要約が始まる
   - LLM にとって `summary` は「確認なしで会話を打ち切る」重い判断になり、保守的に `chat` を選びやすい
2. **終了条件が定性的（「十分な深掘り」）で、継続側にバイアスがかかっている**
   - 「十分」の基準（往復数・観点数など）が定義されていない
   - プロンプト全体は「深い洞察を引き出す」「深掘りテクニック」が大半を占め、終了に関する記述は数行のみ
   - 「深掘りが十分でない場合は `chat`」という否定条件が先に来る
3. **bulk モードでは全問完了後に「深掘りフェーズ開始」を宣言させるため、そこからの終わりどころがない**
4. **時間による打ち切りも受け身**
   - `estimated_duration` 未設定ならタイムマネジメント指示自体が入らない
   - 設定されていても、超過後に AI から終了を提案する指示はない
5. **LLM は自分が何往復深掘りしたかを正確に数えられない**
   - 進捗欄には事前定義質問の完了数しか出ておらず、深掘りの量はプロンプト上に見えない

## 国政版（本家 team-mirai/mirai-gikai）との比較

`origin/kokusei/develop`（2026-10-07 時点、`packages/shared/src/interview-prompts/` に集約）を確認した。

- **終了判定（ステージ遷移ガイダンス・活用ルール・タイムマネジメント）は北海道版と同一の文面**。本家でも同じ傾向が出ると考えられる
- 北海道版に未取り込みの関連差分:
  - `COMMON_STOP_CRITERIA`「深掘りの打ち切り基準」(#585): 具体例を1〜2つ得たらその方向は十分、同方向に3回以上連続で掘らない、政策論から離れた・「場合による」が出た・話題転換を求められたら打ち切る

  - targeted モード (#818)

## 検討すべき論点

### 論点1: 終了の主導権を誰が持つか

| 選択肢 | 内容 | メリット | デメリット |
|---|---|---|---|
| A. LLM 判断のまま、基準を具体化 | プロンプトの「十分」を定量・定性的に定義する | 実装が小さい | LLM の揺らぎは残る |
| B. LLM が「終了確認」を挟む | 区切りで「他にお伝えしたいことはありますか？なければレポート作成に進みます」と聞き、ユーザーの回答で `summary` に進む | `summary` 判断が軽くなる。ユーザーが納得して終われる | 1往復増える。確認の頻度が多いとうるさい |
| C. コード側で決定的に制御 | 全問完了後の深掘り往復数や経過時間が閾値を超えたら、プロンプトで終了確認を強制する | 確実に終わる | 熱心に話しているユーザーを遮るおそれ |
| D. UI で終了導線を強化 | 一定条件で「レポートを作成する」ボタンを目立たせる／クイックリプライに「終了する」を出す | LLM に依存しない | AI 側から「終了しますか？」と聞く体験ではない |

組み合わせ（例: C で区切りを判定し、B の形で確認、D でクイックリプライを出す）も可能。

### 論点2: 「十分な深掘り」の基準をどう定義するか

- 往復数ベース（例: 全問完了後に深掘り3〜5往復）
- 観点ベース（例: 賛否・理由・自分への影響・懸念/期待のうち一定数が得られたら）
- 回答の質ベース（短文回答・「特にない」が続いたら終了）
- 時間ベース（`estimated_duration` に対する経過時間）
- これらを LLM の判断に任せるか、コードで数えてプロンプトに埋め込むか

### 論点3: 終了確認のタイミングと文言

- 全問完了直後に一度確認するか、深掘りを数往復してから確認するか
- 確認を断られた（「まだ話したい」）後、次に確認するまでの間隔
- 文言案: 「ここまでたくさんお話しいただきありがとうございます。ほかにお伝えしたいことはありますか？なければ、これまでの内容をレポートにまとめます」
- 確認時にクイックリプライ（「レポートを作成する」「もう少し話す」）を出すか
  - 現状 bulk/loop のプロンプトでは、事前定義質問以外でクイックリプライを使えない（国政版は選択肢形式なら深掘りでも可に変更済み）

### 論点4: モード別の扱い

- bulk: 「移行の合図」で深掘りフェーズを宣言させている。深掘りフェーズの上限を設けるか、宣言自体を変えるか
- loop: 各テーマで 2〜3 回のフォローアップを推奨しているため、全体の往復数は bulk より多くなる。全問消化を前提にするか
- モード別に基準を変えるか、共通の基準にするか

### 論点5: 時間（`estimated_duration`）の扱い

- 本番の各議案の `interview_configs.estimated_duration` の設定状況（**要確認**）
- 未設定時のデフォルトを設けるか
- 超過時に AI から能動的に終了を提案するか（現状は受け身）

### 論点6: 国政版との関係

- 終了条件は本家と同じ文面のため、北海道版で独自に変えると以後の本家取り込み時に差分管理が必要になる
- 本家の `COMMON_STOP_CRITERIA` などを先に取り込むか、プロンプト共通化（`packages/shared/src/interview-prompts/`）ごと追従するか
- 北海道版での改善を本家に還元（Issue / PR）する余地

### 論点7: 検証方法

- 国政版にはインタビューシミュレーション（#761）がある。取り込めば、ペルソナを変えて終了までの往復数を比較できる
- 取り込まない場合は、手動で数パターン（協力的・短文回答・脱線しがち）を試して往復数と体験を確認する
- 既存の `stage-transition-guidance.test.ts` などで、プロンプトに終了確認の指示が入ることをテストする
