## 3. 詰まったところ

### 3-1. `seed:master` が `TypeError: fetch failed` で落ちる — 8000 番のトンネルが半死

- **症状**: `committees の読み出しに失敗しました: TypeError: fetch failed`。手元の 8000 番は LISTEN しているが、`curl` は接続した後に応答が無くタイムアウトする
- **原因**: 8000 番を `ssh -N -L 8000:127.0.0.1:8000 ezocivic-vps1`（keepalive 無し）で張っていた。
  WSL のスリープや NAT のタイムアウトで TCP が死んでも ssh のプロセスは残り、ローカルのポートを掴み続ける。
  5433 は `ServerAliveInterval` 付きで張っていたので生きていて、`psql` は通っていた
- **切り分け**: VPS 側で `curl 127.0.0.1:8000/auth/v1/health` は 200。別ポート（18000）に張ったトンネルもすぐ 200 → 手元のトンネルだけが死んでいる
- **対処**: 古い ssh を `kill` し、keepalive 付きで張り直す

```bash
ssh -f -N ezocivic-vps1 \
  -L 127.0.0.1:5433:127.0.0.1:5433 \
  -L 127.0.0.1:8000:127.0.0.1:8000 \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3
```

- **教訓**: `psql` が通ることは 8000 番が生きている根拠にならない。流す前に `curl -s -m 5 http://127.0.0.1:8000/auth/v1/health` を見る

### 3-2. トンネルが何度も消える・二重に張られる

- **症状**: 作業の途中で `psql` が `Connection refused`（5433 が無い）や、`curl` が `Connection refused`（8000 が無い）になる。これを3回くらい繰り返した
- **原因**:
  - `kill` で止めるときに、生きている方のトンネルまで一緒に止めた
  - シェルの履歴から、keepalive 無しの古い `ssh -N -L 8000:...` を呼び出して張り直していた
  - 古い形のコマンドはローカル側に `127.0.0.1:` が無いので、`bind [::1]:8000: Cannot assign requested address` が出る（害は無いが紛らわしい）
  - `-f` を付けて2回実行すると、2回目は `Address already in use` で失敗する。1回目は成功しているので、これは害が無い
- **対処**: まず `pgrep -af "^ssh "` で今あるトンネルを見てから、止めるか張るかを決める。
  止めるときはポート番号で絞る（`pkill -f "127.0.0.1:8000:127.0.0.1:8000"`）
- **おすすめ**: `~/.ssh/config` にトンネル専用のホストを作っておくと、長いコマンドを打ち間違えない

```
Host vps-tunnel
  HostName 153.127.41.244
  User ubuntu
  LocalForward 127.0.0.1:5433 127.0.0.1:5433
  LocalForward 127.0.0.1:8000 127.0.0.1:8000
  ExitOnForwardFailure yes
  ServerAliveInterval 30
  ServerAliveCountMax 3
```

張るときは `ssh -f -N vps-tunnel`、止めるときは `pkill -f "ssh -f -N vps-tunnel"`。

### 3-3. `psql` がローカルのソケットに繋ごうとする — `PROD_DB_URL` が空

- **症状**: `connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed`
- **原因**: 新しいターミナルで実行していて、`PROD_DB_URL` が空だった。空だと `psql` は手元の Unix ソケットに繋ごうとする
- **見分け方**: エラーにソケットのパス（`/var/run/postgresql/...`）が出たら変数が空。`127.0.0.1, port 5433 ... Connection refused` ならトンネルが落ちている
- **対処**: そのターミナルで `export` し直す。`echo "${PROD_DB_URL%%:*}"` が `postgresql` を返すか先に見る

### 3-4. 管理者作成の curl が 401 `no_authorization`

- **症状**: `{"code":401,"error_code":"no_authorization","msg":"This endpoint requires a valid Bearer token"}`
- **原因**: そのターミナルで `SUPABASE_SERVICE_ROLE_KEY` が空で、`Authorization: Bearer ` の後ろが空になっていた（3-3 と同じく、ターミナルごとの `export` の問題）。
  もう1つ、手順書の curl は `$SERVICE_ROLE_KEY` を使っていて、`seed:master` の節で export する `$SUPABASE_SERVICE_ROLE_KEY` と名前が食い違っていた
- **対処**: `echo ${#SUPABASE_SERVICE_ROLE_KEY}`（180 前後なら入っている）を見てから実行する。手順書の変数名は PR #59 で揃えた

### 3-5. `read -p` の案内文にパスワードを書いてしまう

- **症状**: `read -rs -p "<パスワード>: " ADMIN_PW` と実行した。パスワードが画面とシェルの履歴に残り、`ADMIN_PW` には何も入らなかった
- **原因**: `-p "..."` は画面に出す案内文で、入力欄ではない
- **対処**: 案内文は書き換えずに `read -rs -p "管理者パスワード: " ADMIN_PW` のまま実行し、出てきたプロンプトにパスワードを打つ。
  履歴やログに出たパスワードは使わない

### 3-6. `htpasswd: command not found` — 手元で実行していた

- **原因**: `sudo htpasswd ...` を手元の WSL（`shuig@my-windows-pc`）で実行していた。htpasswd は VPS にしか入れていない
- **見分け方**: プロンプトで判断する

| プロンプト | ここで打つもの |
|---|---|
| `shuig@my-windows-pc`（手元） | `psql "$PROD_DB_URL"`、`curl http://127.0.0.1:8000/...`、`pnpm seed:*`、トンネルの `ssh -f -N` |
| `ubuntu@ezocivic-vps1`（VPS） | `sudo htpasswd`、`sudo apt`、nginx / certbot の操作 |

### 3-7. htpasswd が空ファイルになる

- **症状**: `htpasswd: password verification error` の後、`/etc/nginx/htpasswd-gikai` が 0 バイトで残った
- **原因**: 2回目の確認入力が1回目と一致しなかった。`-c` はファイルを先に作るので、空のファイルだけが残る
- **対処**: もう一度 `sudo htpasswd -c ...` を実行し、`sudo cat` で `ユーザー名:$apr1$...` の1行があるか確かめる。
  パスワードを忘れたときは `-c` を付けずに実行して付け直す（`-c` を付けるとファイルを作り直す）。合っているかは `sudo htpasswd -v <ファイル> <ユーザー名>` で確かめられる。
  なお PR #64 で、web 用（`htpasswd-gikai-web`）と admin 用（`htpasswd-gikai`）の2ファイルに分けた

### 3-8. https が vhost に届かない（gikai が 200、db が 404）— certbot が `default` に書き込んだ

- **症状**: `https://gikai.ezocivic.tech/` が 200（nginx の Welcome ページ）、`https://db.ezocivic.tech/auth/v1/health` が 404
- **原因**: vhost を置く前に certbot を一度流していて、証明書と 443 番の server ブロックが apt で入る `default` サイトに書き込まれていた。
  あとから置いた3つの vhost は 80 番しか待ち受けていなかった
- **対処**:
  1. `default` を `sites-enabled` から外し、`/etc/nginx/default.certbot-bak` に退避した
  2. どの vhost にも当たらない通信を切る `00-default.conf`（`listen 80 default_server; return 444;`）を置いた
  3. certbot を流し直し、「1: Attempt to reinstall this existing certificate」を選んだ（証明書を取り直さないので、発行回数の制限を使わない）
- **教訓**: certbot は必ず vhost を置いた**後**に流す。`default` は先に外す

### 3-9. https でも 301 が返り続ける — 443 番のブロックに転送が入った

- **症状**: 3-8 を直した後、`https://db.ezocivic.tech/...` も `https://gikai.ezocivic.tech/` も 301
- **原因**: certbot の reinstall で、80 番用の `if ($host = ...) { return 301 https://...; }` が **443 番の server ブロックにも**入っていた（db と gikai）。
  https で来ても https へ転送し続ける
- **対処**: 443 番側の `if` ブロック（3行）を消した。確認は `grep -c "return 301" /etc/nginx/sites-available/*.ezocivic.tech.conf` で3つとも 1
- **失敗したこと**: 3つのファイルすべてに「最初の `if` ブロックを消す」操作をかけたところ、gikai-admin はもともと正常で
  （443 番に `if` が無かった）、残すべき 80 番の転送を消してしまった。退避しておいた `.bak` から戻した。
  **一括で直す前に、ファイルごとに `grep -n "server {\|if (\$host\|listen"` で構造を確かめる**
- 退避ファイル（`/etc/nginx/*.bak`、`/etc/nginx/default.certbot-bak`）は、動作確認が済んだので消して構わない

### 3-10. 「seed の議案は架空」という記述が古かった

- 手順書 §1 に「seed の議案は架空のサンプルなので VPS に流さない」と残っていた。
  実際は PR #44（2026-09-24）で、札幌市議会の実データ（令和8年第1回〜第3回定例会、129件）に置き換わっている
- 本番に入れるコマンドは PR #60 の `pnpm seed:bills`（削除しない・冪等・既定は dry-run。先に `seed:master` が必要）。
  `pnpm seed` は全件を削除してから入れるので、本番には使わない
- 手順書は PR #63 で直した

### 気にしておくこと

- 作業中に、本番の `SERVICE_ROLE_KEY` とパスワード1つがチャットのログや画面に出た。
  出たパスワードは使っていない。`SERVICE_ROLE_KEY` は公開前に作り直すか判断する。キーは `JWT_SECRET` で署名した JWT なので、古いキーを無効にするには `JWT_SECRET` から変える必要がある。その場合は `ANON_KEY` も作り直し、compose の `.env`・web.env / admin.env・GitHub の Variables（`NEXT_PUBLIC_SUPABASE_ANON_KEY`）をすべて差し替える
