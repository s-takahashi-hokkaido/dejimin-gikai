## 3. 詰まった点

### 3-1. DNS の委任先とゾーンの置き場所が食い違っていた

**症状**: `ezocivic.tech` がゾーンごと SERVFAIL で、名前解決が一切できない。

**原因**: Xserver にはネームサーバーが2系統ある。レコードは片方に入っていたが、
ドメインの委任先はもう片方を向いていた。

| ネームサーバー | 用途 | ゾーンを置く条件 |
|---|---|---|
| `ns1〜5.xserver.jp` | エックスサーバー**レンタルサーバー**用 | レンタルサーバーの契約が要る |
| `ns1〜3.xdomain.ne.jp` | **Xserverドメイン**（ドメイン単体）の無料DNS | ドメインを持っていれば使える |

**切り分け方**: 委任先のネームサーバーに直接聞く。**REFUSED は「そのゾーンを持っていない」**という
応答なので、レコードの中身が違うのではなく**ゾーンごと無い**と分かる。

```bash
nslookup -type=NS ezocivic.tech ns01.trs-dns.com   # レジストリが持つ委任先
nslookup -type=A gikai.ezocivic.tech ns1.xdomain.ne.jp  # ゾーンがある側に直接聞く
```

**直し方**: 委任先を、ゾーンが実在する `ns1〜3.xdomain.ne.jp` に変更した。レコードは触っていない。

### 3-2. `ssh` 越しの `sudo` は `-t` が要る

**症状**: 手順7-1 で失敗する。

```
sudo: a terminal is required to read the password
```

**原因**: `ssh host 'command'` は端末を割り当てないので、`sudo` がパスワードを聞けない。

**直し方**: `-t` を付ける。→ 手順書 手順7-1 に反映済み。

```bash
ssh -t ezocivic-vps1 'sudo mkdir -p /srv/supabase && sudo chown ubuntu: /srv/supabase'
```

### 3-3. SSH トンネルが「半死」になる

**症状**: `npx supabase migration up` が `Connection timed out`。しかし `ssh` のプロセスは生きていて、
ローカルの 5433 も待ち受けているので一見正常に見える。

**原因**: WSL のスリープや NAT のタイムアウトで TCP が死んでも、keepalive が無いと ssh が気づかない。
VPS 側で見ると、送信キューが溜まったまま ACK が返らない接続が残っていた。

```
Recv-Q  Send-Q  Local Address:Port    Peer Address:Port
0       148     153.127.41.244:22     <自分のIP>:43244   ← 半死
```

**切り分け方**: **TCP が繋がるだけでは判断できない**。ssh はリモートに届かなくてもローカルの接続は
受け付けるため。Postgres と実際に握手するのが確実。

```bash
psql "$PROD_DB_URL" -c "select version()"   # これが通れば本物
```

**直し方**: keepalive を付けて張り直す。→ 手順書 手順8 に反映済み。

```bash
ssh -f -N ezocivic-vps1 \
  -L 127.0.0.1:5433:127.0.0.1:5433 \
  -L 127.0.0.1:8000:127.0.0.1:8000 \
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3
```

### 3-4. `ssh -N` は「固まった」ように見える／`export` はターミナルごと

同じ場面で続けて2つ踏んだ。

- **`-N` はプロンプトを返さない。** トンネルを保つためのオプションなので、使っている間ずっと前面に居座る。
  **`-f` を付ければ背景に回る。** 付け忘れて止まって見える時は `Ctrl+Z` → `bg` でそのまま背景に送れる
- **local 側に `127.0.0.1:` を付けないと** `bind [::1]:5433: Cannot assign requested address` が出る。
  WSL に IPv6 ループバックが無いため。無害だが紛らわしい
- **`export PROD_DB_URL=...` は別のターミナルに引き継がれない。** 空のまま `--db-url ""` で実行すると、
  `failed to connect to host=127.0.0.1` という紛らわしいエラーになる。`echo "${PROD_DB_URL%%:*}"` が
  `postgresql` を返すか先に見る

いずれも手順書 手順8 に反映済み。

### 3-5. OS 再インストールでパケットフィルターが 22 番のみに戻る

**症状**: 80 / 443 が外から閉じている。`ufw` は active で許可しているのに届かない。

**原因**: さくらのパケットフィルターは**コントロールパネル側の設定で、OS 再インストール時に
引き継がれない**。再インストール直後の既定は 22 番のみ許可。

**気づき方**: 手順9 の certbot まで進んでから気づくと手戻りが大きい。**手順3 の直後に外から叩いて確かめる**。
→ 手順書 手順1 に注意を追記済み。

### 3-7. `seed:bills` が毎回129件を無駄に更新していた

**症状**: 実装直後に dry-run したら、**全129議案が「差分あり」**と出た。

```
~ 議案第23号|bill (published_at)
~ 議案第24号|bill (published_at)   ... 129件
```

**原因**: seed は `2026-03-01T00:00:00+09:00`、PostgREST は同じ時刻を `2026-02-28T15:00:00+00:00` で
返すため、文字列のまま比べると一致しない。

**直し方**: 両側を UTC の ISO 文字列に揃えてから比較する（`normalizeTimestamp`）。
データは壊れないが、放置すると「冪等」の約束が崩れ、計画の表示も読めなくなる。

> **timestamptz を文字列で比較しない。** 同じ瞬間でも表記が変わる。

### 3-8. トピック分析が公開前の VPS で 401 になる

**症状**（PR #53 のレビュー中に発見）: admin のトピック分析は、Server Action から
**admin 自身を公開URLで HTTP 呼び出し**する作りだった。公開前は nginx が admin の全パスに
Basic 認証をかけるため、このサーバー間 fetch が 401 で弾かれ、解析が1フェーズも進まない。

**なぜ環境変数で逃がせないか**: 使っていたのは `NEXT_PUBLIC_APP_URL` で、
**`NEXT_PUBLIC_*` はビルド時に JS へ埋め込まれる**ため、VPS の env ファイルでは差し替えられない。

**直し方**: サーバー専用の `ADMIN_INTERNAL_URL`（`http://127.0.0.1:3003`）を足して優先させた（PR #56）。
admin → web の revalidate（PR #51 の `WEB_INTERNAL_URL`）と同じ構図で、手順書 §6 #3 が
admin → web だけを対象にしていたため漏れていた。

> **Basic 認証を全パスにかけると、自分自身を公開URLで呼ぶ経路が全部止まる。**
> 公開URLで自分を叩いている箇所が他にないか、公開前に grep して確かめる。

### 3-9. sudoers の前提が誤っていた（訂正）

当初 PR #53 で「Ubuntu のクラウドイメージは `/etc/sudoers.d/90-cloud-init-users` で
`ubuntu ALL=(ALL) NOPASSWD:ALL` を与えるので、`gikai-deploy` の1行では sudo を絞れない」と書いた。

**実機で確かめたところ、この環境には当てはまらなかった。**

```
$ ls -la /etc/sudoers.d/
-r--r-----  1 root root 1068 Jan 30  2024 README     ← README しか無い
$ sudo -n -l
sudo: a password is required                          ← NOPASSWD が効いていない
```

さくらのVPS の Ubuntu 24.04 標準OSインストールには `90-cloud-init-users` が無い。つまり
**`gikai-deploy` は実際に効く**（デプロイ鍵で通るのは `systemctl restart` だけ）。
一方でこれは §3-6 の2回目の失敗の原因でもある。

手順書・`infra/README.md`・`infra/sudoers/gikai-deploy` の3箇所を訂正済み（PR #58）。

> **他のイメージや別のVPSへ移す時は、この前提が変わっていないか `sudo -n -l` で確かめる。**

### 3-10. 会話ログがバックアップに最大14日残る

**症状**（PR #54 のレビュー中に発見）: `pg_dump -n public` は `chat_logs` を含み、バックアップは14日保持する。
つまり DB から90日で消した会話ログが、バックアップの中に最大14日生き延びる。
プライバシーポリシー文案の「AI チャットのやり取りは 90 日で自動的に削除します」と食い違う。

**直し方**: `pg_dump` から `-T public.chat_logs` で除外した。`chat_logs` を参照する外部キーが
無いことを確認済みなので、復元時に他テーブルへ影響しない。復元しても会話ログは戻らないが、
分析用の一時データなので戻せなくてよい、という判断。

> **保存期間を約束する時は、バックアップの保持期間も足して考える。**

### 3-11. SSH に総当たりが来ている

立ち上げ直後から、海外のIPが 22 番にログインを試み続けている（確立済み接続が同時に3本）。
**手順2 で公開鍵認証のみにしてあるので入られることはない**が、ログは汚れる。

```bash
ss -tn state established '( sport = :22 )'                        # 自分以外のIP
sudo journalctl -u ssh --since today | grep -c "Invalid user\|Failed"
```

対策は §7「決めること」に案を3つ書いて判断待ち（PR #59）。
